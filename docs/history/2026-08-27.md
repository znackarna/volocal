### 2026-08-27 — The window is zoomed, not scaled, and the fix that caused it goes

He saw the toolbar pills on the live site with their arcs heavier than their
sides — the fault fixed on 19 August and written down as fixed. Then the sentence
that solved it: **only in Firefox, and only on the site; not in the preview.**

`transform: scale()` scales a picture. The subtree is rasterised and the result
resampled down, which a straight 1 px edge survives and a curve does not: the
resampling piles coverage into the arc. `will-change: transform` fixed that in
Chrome, which re-rasterises a promoted layer at the scale it is composited at.
It was measured there, at device scale 1, and the note on it is honest about
what it measured.

**Firefox does the opposite with the same rule.** A promoted layer is rasterised
once and its texture is scaled, so the hint that fixed Chrome is what caused
Firefox. The page has therefore been clean for whoever built it and heavy-armed
for everybody on Firefox since 19 August — the worst shape a defect can have.

`zoom` is not a picture. It scales used values, so the window is laid out at the
size it is shown at and every edge is drawn rather than resampled. There is no
texture, which is why `will-change` went with the transform: a layer would only
give the compositor something to scale again.

**Chosen by looking, not by reasoning.** A card with the same window three
times — transform with the hint, transform without it, and `zoom` — at the
page's own 0.92, opened in Firefox. Only `zoom` was clean; the first two were
identical, which also says the hint does nothing there but harm.

`fit()` in `preview.js` writes the factor now as `zoom`. Its measurement is
unchanged and that was checked rather than assumed: under `zoom`, `offsetWidth`
still reports the unzoomed 1180 while `getBoundingClientRect` reports the drawn
size, which is exactly the pair `fit()` and `layoutWaves()` already rely on.

The first two attempts at seeing this failed and both are worth remembering: a
test card with one pill in a 150 px stage showed nothing, because the fault
lives on long edges and large arcs; and Firefox headless would not take a
screenshot here, so the only eyes on it were his.

### 2026-08-27 — The release script asks about the tree before it builds, not after

Codex's item 1, and the strongest finding in that brief. `release.ps1` ran its
checks and then built the installer, and asked whether the tree was committed
only in the second pass, twenty minutes and one human step later.

**Asking afterwards is not a guard.** The build takes what is on disk. Stash the
uncommitted part and the tree is clean and still at the same commit, so the
later check passes over an installer nobody can account for — and both things
that vouch for it, the version in the file name and the commit in
`built-from.txt`, agree with it, because both were true of a tree that no longer
exists.

It also cost twenty minutes yesterday in the ordinary direction. The build
rewrites `Cargo.lock` with the new version; that file was still uncommitted when
the second pass ran, and committing it moved `HEAD` away from the installer, so
the whole build had to run again. A check that sits that late punishes the
honest case and misses the dangerous one.

`Assert-CleanTree` is one function called by both passes — one implementation,
because two spellings of one rule is how the passes come to disagree about what
clean means. `git status --porcelain` already reports all three states that must
be refused and reports no ignored file, so what `.gitignore` covers is allowed
by construction; what it did not do was say which files, which is the difference
between a stop and a useful one.

Driven rather than reasoned about, in a throwaway repository, against the real
function lifted out of the script: a clean tree is allowed, a modified tracked
file, a staged file and an untracked source file are each stopped, and a tree
dirty only with an ignored file is allowed. The refusal was read back with all
three kinds present at once and names every path under its own heading.

`-SkipChecks` still gets past it and now says out loud what it is doing.

Files: `scripts/release.ps1`.

### 2026-08-27 — And a fallback, because `zoom` is four years younger than the page's other rules

He asked the question worth asking about any fix for one browser: does it cost
anything anywhere else. One thing, and it was mine to have caught before he did.

**Firefox learned `zoom` in version 126, May 2024.** Anything older ignores the
property entirely — and ignoring it does not mean falling back to the old
behaviour, it means a 1180 px window standing at full size inside a frame that
is 1114 px wide, cropped by `overflow: hidden`. A worse fault than the one being
fixed, and a silent one.

`fit()` now asks `CSS.supports("zoom", "0.5")` and writes the transform where the
answer is no. That fallback is not the state this replaces: the resampling was
what an engine does to a **promoted** layer, and `will-change` is gone, so an old
Firefox gets a plain transform, which is what it drew correctly before anybody
promoted anything. `transform-origin: 0 0` stays on the stage for that one path
and says so.

Everything else `zoom` touches was checked rather than assumed: `offsetWidth`
reports 1180 whatever the zoom, the frame comes out 1114 × 702 as it did before,
and nothing is promoted any more.

### 2026-08-27 — The footer's own padding had never applied

Two things from one comment, and the second is the interesting one.

**The mark and the sentence are centred on each other.** `baseline` was wrong and
he read it exactly right: a baseline puts the drawing's floor on the text's
baseline, so the letters ride above the shapes and the line looks like it is
flying upward. The drawing is 12 px in a 20 px line box, so centring the boxes
is what centres them to the eye. Measured: the two centres are the same number.

**And the page ended on the window's edge**, which he asked for as the header's
own air. The rule that should have provided it was there and had never applied:

```
.wrap   { max-width: 1180px; margin: 0 auto; padding: 0 32px; }   /* 0,1,0 */
footer  { padding: 96px 0 72px; }                                 /* 0,0,1 */
```

A class outranks a type, so `.wrap` overrode the footer's padding in full --
horizontal padding and all -- from the day the page was written. What has held
the air above the footer all this time is the closing section's own 96 below
itself, and the 72 under it was never there. The header escaped the same fate by
being written `header.top`.

It is `footer.wrap` now, with the two vertical values named separately so the
gutters stay where the wrapper puts them. Below the footer: 104 px, the same as
under the header, measured on both.

**The lesson is the one `CLAUDE.md` already has** in another form -- two rules
that differ only in file order must say so. This is its neighbour: a rule that
loses on specificity does not fail, it simply never happens, and it goes on
looking like the reason for whatever the page does.
