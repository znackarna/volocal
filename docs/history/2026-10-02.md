# 2026-10-02

### 2026-10-02 — The page can be served from our own server, and Vercel keeps serving it until the address moves

The owner is moving the company's sites off Vercel onto `znackarna-server2`,
which runs Next.js applications behind Caddy and nothing else: it installs the
packages, runs `next build` and starts `next start`. The page has no build step,
so it needed something for that server to start.

**What was added.** `site-server/`, a Next.js application of one route handler
that reads `docs/site` from disk on every request. Nothing in `docs/site`
changed and nothing is copied out of it. It does what `site.yml` does on the way
to Vercel:

- serves the same files `site.yml` copies into `_site`, and nothing else in
  `docs/site` (`translate.mjs`, `en.json`, `bundle.py` and the rest answer 404);
- makes the English page with `translate.mjs`, once per process;
- writes the latest release into *Verze* and *Version*, asking GitHub's API
  every ten minutes. `site.yml` redeploys when a release is published, and the
  server hears nothing about releases — a release is published by hand, hours
  after the commit that carries its number, so a number read only at build time
  would stay one release behind;
- refuses to build when `site.yml` would have refused to deploy: a sentence with
  no English, or anything but two version mentions in either page. A failed build
  on that server leaves the previous version running, which is what a failed
  `site.yml` job does on Vercel.

`/en/` stays `/en/` (`skipTrailingSlashRedirect`), because that is the address in
the page's canonical and hreflang links. Files are answered with Vercel's own
default, `public, max-age=0, must-revalidate`, and an ETag, so a returning reader
gets a 304.

**What it does not do.** Vercel's Web Analytics script, `/_vercel/insights/script.js`,
exists only on Vercel; on the server it answers 404 and nothing is counted.
Choosing a replacement is the owner's decision, not part of this change.

**Why not `output: 'export'`.** That writes static files, and `next start` refuses
to run with it; the server starts every application with `next start`. **Why not
`public/`.** The server runs `next build` directly, without the package's own
build script, so nothing would copy `docs/site` into it.

Vercel is untouched: `site.yml` deploys from `docs/site` as before and never looks
at `site-server/`.

**Verified** with `next dev` (no production build on the shared machine): `/`,
`/index.html`, `/en/`, `/en` and `/en/index.html` answer 200 with *Verze 1.2.26*
and *Version 1.2.26*, the latest release; the English page asks for
`../brand.css`; stylesheets, scripts, fonts with their licences, both cards,
`robots.txt` and `sitemap.xml` answer with their types; the tools in `docs/site`,
`README.md`, an unknown path and `/fonts/%2e%2e/en.json` answer 404; a repeated
request with the ETag gets 304. The build check passed on the page as it is, and
refused a copy of it with one translation removed, with `translate.mjs`'s own
message.

### 2026-10-02 — A plan for a command line

He asked whether Volocal could have a command-line interface, then what it could
reach and whether it would need documentation. Measured rather than guessed: the
archive (`db.rs`) and the export formats (`export.rs`) have no tie to the window
at all; transcription, speaker separation, import, the language model and
downloading are tied to it only by reporting progress through `app.emit`.
Recording from a microphone, playback and editing by hand belong to the window
and are not offered.

His two decisions: **English command names, and the application's own
archive** — so a recording transcribed from a terminal shows up in the window.
The second rests on something checked first: the archive runs in WAL with a
five-second busy timeout, so two processes sharing it is safe.

`docs/cli.md` is to be generated from the program's own `--help` and held to it
by `docs-check.mjs`, so the documentation cannot drift from the commands.

Written down as `docs/cli-plan.md` in four phases, nothing started. It is not
among the six planned features, so where it goes in that order is his to say.

Files: `docs/cli-plan.md`.

### 2026-10-02 — The command line leaves the window alone

His reshaping of the plan an hour old: a command line that does useful things
**without changing how the window works**, and later a build with no window at
all. Better than the first plan, which put one progress interface through the
window's own transcription code.

Checked before agreeing, by what each module imports: `db.rs`, `export.rs`,
`tools.rs`, `speakers.rs`, `languages.rs` and `voiceprint.rs` have no tie to
Tauri. Most of the engine never knew there was a window. So the command line
uses the engine and writes **its own small driver**, repeating a little
orchestration on purpose so the window's stays exactly as it is.

The second half decides the structure. A build with no window must not link
Tauri, so the command line is a separate console program over a library that
knows nothing about windows — and the window becomes the other program on top of
it. Two prices named in the plan: the crate becomes a library, and `Run` in
`whisper.rs` stops requiring an `AppHandle` it carries but never uses.

Files: `docs/cli-plan.md`.

### 2026-10-02 — The engine is a library, and the window is unchanged

Stage 1, step 1 of `docs/cli-plan.md`: for a second program to use the engine,
it has to be a library. `src/main.rs` became `src/lib.rs`, its `fn main()`
became `pub fn run()` and was otherwise not touched, and the new `src/main.rs`
is the three lines that call it. This is the shape Tauri's own templates use,
and it was chosen over carving the engine out module by module because every
`crate::` path inside it keeps meaning exactly what it meant — the window's code
was moved, not edited.

The library is named `volocal_lib`. A library and a program of one name write
the same `.pdb` on Windows and the second build overwrites the first's debug
symbols; Tauri names theirs `*_lib` for the same reason. `default-run` keeps
`volocal` the program cargo starts.

**Public is only what the command line will use.** The first attempt made every
module public and the compiler objected — `commands` is the window's own door
into the engine, typed against `AppState`, which is crate-private, and nothing
outside should reach it. `commands`, `ai_edit`, `download` and
`online_import` stay private; `db`, `export`, `tools`, `transcription`,
`voiceprint`, `diagnostics` and `user_message` are public.

Proved rather than assumed: **317 Rust tests and 4 ignored, the same count as
before the move**, now running from `src\lib.rs`; clippy with `-D warnings` and
fmt clean; and the window started from the new library in `tauri dev` and stayed
up.

Files: `src-tauri/src/lib.rs` (was `main.rs`), `src-tauri/src/main.rs`,
`src-tauri/Cargo.toml`.

### 2026-10-02 — `volocal-cli`, the commands that read

A console program beside the window, over the same engine and the same
archive: `status`, `list` (with `--search` and `--folder`), `show`, `export` to
TXT, Markdown, SRT, VTT or JSON, and `export-audio` to MP3, M4A or WAV.

**Three things the window had and the command line could not borrow.**

*Finding the archive.* The window's `archive_path` asks Tauri for the profile
folder and, on the way, finishes the two renames left from when this was Whisp.
That is the window's start-up work, done once; the command line opening the
archive must not perform a migration behind its back. `find_archive` looks in
the same places in the same order and moves nothing. It names the profile folder
rather than asking Tauri, so a test holds `IDENTIFIER` to `tauri.conf.json`.

*Writing audio.* `export_audio` lived in the window's private `commands`. The
body after reading the archive was already free of the window, so it moved
unchanged into `export::audio`, and the command became the part that reads the
source and the settings.

*The words for an error.* The engine returns codes; the text lives in the
window's dictionary. The command line reads the English half of it
(`src/locales/en/errors.ts`) at build time rather than carrying a second set of
sentences, so a message says the same thing in both programs.

**Two decisions a command line owes a script.** An existing file is never
overwritten without `--force` — a command run twice must not quietly destroy the
first result. And search matches, which the window draws as a highlight and the
engine marks `<<like this>>`, are bold in a terminal and taken out in a pipe.

An id may be given as its first few characters, the way `git` takes a short
hash; two recordings sharing them is refused with a request for more.

Run against the real archive, not a fixture: `status` found the archive, ffmpeg,
whisper on Vulkan and 31 GB; `list`, `show` and a search returned the one
recording; SRT, TXT and JSON exported, the JSON parsed; an `.mp4` became a 33 MB
MP3 through ffmpeg; a second export without `--force` was refused; an unknown
format, an unknown id and a missing archive each said so and exited 1.

318 engine tests (one new, the identifier), 5 for the command line, clippy and
fmt clean, 335 frontend.

`clap` is new, and only the command line uses it; `docs/cli.md` will be
generated from the help it produces.

Files: `src-tauri/src/bin/volocal-cli.rs`, `src-tauri/src/lib.rs`,
`src-tauri/src/export.rs`, `src-tauri/src/commands/folders.rs`,
`src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `docs/cli-plan.md`.

### 2026-10-02 — Correction: the program was not in its own commit

`0e59e70` described `src-tauri/src/bin/volocal-cli.rs` and did not contain it.
`.gitignore` carried `bin/` for the tools folder — ffmpeg and whisper, gigabytes
of third-party programs — and unanchored, that matches every folder called
`bin`, including the one Cargo looks in for a project's second program. `git add
-A` passed over it in silence; `docs-check` looked for the file on disk, where
it was, and said nothing either.

So for one commit `dev` carried a library, a plan, a history entry and every
change around the command line, and not the command line.

The rule is anchored now — `/bin/` and `/models/` — which keeps the tools out at
the root and lets `src-tauri/src/bin/` in. Checked both ways: the root `bin/`
still shows as ignored, and no other folder called `models` exists for the
anchoring to uncover.

Caught by looking at what the commit held rather than at what it said. Worth
doing after every commit that adds a file: `git ls-files` on the new path.

Files: `.gitignore`, `src-tauri/src/bin/volocal-cli.rs`.

### 2026-10-02 — `docs/cli.md` is the help, and a test holds it there

The command line's reference is not written by hand. `reference()` in
`volocal-cli.rs` builds it from the program's own `--help`, command by command,
and `the_documentation_is_the_help` fails whenever `docs/cli.md` and the help
differ. A command cannot be added, renamed or reworded without the reference
saying so — the discipline `docs-check.mjs` keeps over `SECURITY.md`, held here
by `cargo test`, which CI already runs. `UPDATE_CLI_DOCS=1` writes the file.

Checked that it bites: changing *newest first* to *oldest first* in one
command's description, without regenerating, failed the test with the command to
fix it. Put back, it passed.

The introduction above the help says only what the help does not: where the
program is installed and how to regenerate the page. What the program is and
that the window has to be started once are the help's own first lines, and
saying them twice would have been the sentence restating the one below it.

**Two things written by a heredoc came out wrong and were rewritten with the
editor.** Bash in this environment eats backslashes, the hazard recorded on
20 August: every `\n` in the reference had become a real line break inside the
string, and the bold for search matches had become two invisible control
characters in the source. Both worked; neither could be seen or trusted. They
are `\n` and `\x1b` now, and the file holds no raw control byte.

Files: `src-tauri/src/bin/volocal-cli.rs`, `docs/cli.md`.
