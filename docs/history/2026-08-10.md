### 2026-08-10 — A release is two signatures, and they have to happen in this order

- The updater has been in the application since this afternoon and could only
  ever fail: nothing has been released, so `latest.json` does not exist.
  `scripts\release.ps1` is the other half.
- **Two passes, because one signature needs a human.** A release carries two
  that have nothing to do with each other: Authenticode, which is what stops
  SmartScreen warning about the installer and whose certificate lives on a
  hardware token; and the updater's own minisign signature, which is what an
  installed copy checks before it will accept a download.
- The order is the reason the script cannot be one command. The updater
  signature is over the *bytes of the installer*, so it has to be made after
  Authenticode has touched them. Sign in the other order and every existing
  installation refuses the update — correctly, having noticed the file changed.
  The bundler's own `.sig`, made during the build, is therefore thrown away and
  remade in the second pass.
- Guards, each of which stops the release rather than warning: the version must
  agree across `tauri.conf.json`, `Cargo.toml` and `package.json`, because
  nothing keeps those three in step and a mismatch installs one number while
  reporting another — after which an update is offered for ever, or never; the
  signing key must be where it is expected; the installer must actually carry a
  valid Authenticode signature; and the tag must not already exist.
- The release is created as a **draft**, always. A draft's assets are not
  reachable at `releases/latest/download`, so nothing is offered to anybody
  until a person has looked at the page and pressed publish.
- A trap worth writing down: `tauri signer sign` waits for a password even when
  the key has none, with no prompt a script can answer — it simply hangs. `-p
  ""` is required.
- Tested as far as it can be without publishing: a copy of the script truncated
  before the GitHub step, run against a genuinely Authenticode-signed binary
  borrowed from `System32`. Version check, signature check, updater signing and
  a correctly shaped `latest.json` with the right download URL all came out
  right, and both guards were shown to stop the run — an unsigned file and a
  deliberately mismatched version.
- Also verified, because it is the one thing that cannot be checked later: the
  private key on this machine matches the public key in `tauri.conf.json`. The
  signature and the public key carry the same minisign key id, `GB1PMNQI7`. If
  they had not matched, every release would have been refused by every
  installation and nothing would have said why.
- What is still unproven, and cannot be until the first release exists: that an
  installed copy fetches `latest.json`, accepts the signature and installs.
- Files: `scripts/release.ps1`.

### 2026-08-10 — Deleting a folder asked SQLite for a transaction inside a transaction

- Reported from the running application: deleting a folder together with the
  transcripts in it failed with *cannot start a transaction within a
  transaction: Error code 1: SQL error or missing database*. Nothing was
  deleted — the outer transaction rolled back on the way out, which is the one
  part that behaved.
- Both halves were right on their own. `commands::folders::delete_folder`
  wraps the whole errand in one transaction, because giving up in the middle
  used to leave some recordings deleted and the rest in a folder that was about
  to go. `db::delete_folder` opens one too, because returning the recordings to
  the root and removing the folder are one decision. Put together, the second
  `BEGIN` lands inside the first, and SQLite has no nesting.
- It compiled because `Transaction` derefs to `Connection`: `delete_folder(&tx,
  …)` reads exactly like `delete_folder(&db, …)`. Nothing in the types says one
  of them already holds a transaction.
- Fixed at the pattern rather than the instance. `transaction_unless_in_one`
  asks `is_autocommit()` — true only when nobody holds one — and hands back an
  `Option<Transaction>`; `commit` on `None` does nothing, which is right: the
  caller's transaction is still open and still owns the decision. Applied to
  all three functions in `db.rs` that opened their own: `delete_folder`,
  `move_to_folder`, `recover_interrupted`. The first was today's bug; the other
  two were the same trap waiting.
- Worth stating plainly: this broke deleting *any* folder, with or without its
  contents, because the command opens its transaction either way.
- Three tests under `inside_someone_elses_transaction`, and a mutation check —
  putting the nested `BEGIN` back turns two of them red. The third is the one
  that matters most for the fix being right rather than merely quiet: with the
  caller's transaction rolled back, the folder must come back. It cannot if the
  inner call committed one of its own.
- One detour worth recording. The archive showed one recording where there had
  been four, and the first thought was that the failed delete had taken them.
  It had not — the owner had removed them by hand. Checked before touching
  anything, and worth checking again next time: a string search of the database
  file cannot answer this, because deleted rows sit in free pages and keep
  matching long after they are gone.
- Files: `src-tauri/src/db.rs`.
- Verified: `cargo fmt --check`; `cargo clippy --all-targets -- -D warnings`
  silent; `cargo test` (150, three of them new). Not yet confirmed by pressing
  the button in the application — three attempts to drive the archive there
  landed elsewhere, and the owner has the folder in front of them.

- The owner renamed the product. This entry keeps the old name in its title

  written, and the same is true of every other file in `docs/history/`,
  `BASELINE-0.9.0.md` and `HANDOVER.md` — they were deliberately left out of

- 36 files, 166 occurrences. In prose the name is `Volocal`; the header
  wordmark beside the mark is lower case `volocal`, because that is how the
  wordmark is set. `Slobot.exe` became `Volocal.exe`, `slobot-log.txt` became
  `volocal-log.txt`, the crate and npm package are `volocal`, and the updater
  feed points at `znackarna/volocal`.
- **The identifier changed too, and that is the part with teeth.** It decides
  the profile folder, and everything an installed copy owns is in there: the
  archive, its backups, the recordings it made, the playback cache, the log.
  `cz.znackarna.whisp` became `cz.znackarna.volocal`, and without help the first
  Volocal build would have opened an empty archive beside a full one — which
  to somebody with a year of transcripts is indistinguishable from an
  application that lost them.
- So `profile_folder` in `main.rs` moves the folder over, once, before anything
  is opened. `rename` rather than a copy: both paths are siblings under
  `%APPDATA%`, so it is atomic on one volume and there is no moment when the
  data exists twice or half. If the move cannot happen the old folder is left
  untouched and opened where it stands — a rename that fails must not cost
  anybody their work.
- Five tests, and a mutation check that they can fail: an archive under the old
  name is brought over whole (not only the database); a first run finds nothing
  and does nothing; a folder already under the new name is left alone and the
  old one is not swept away either; an empty new folder — what Tauri leaves
  behind — is not in the way; and a move that cannot happen opens the old
  folder in place.
- Then run for real, on the owner's own 520 MB archive, and run **twice**: the
  folder was renamed back by hand and the application started again, which is
  the only way to see a once-only migration a second time. Both times the
  archive arrived complete and the settings came up as they were.
- The second run found a defect the first had hidden: the move was written to
  no log. `diagnostics::set_file` arms the log file *inside* the folder being
  moved, so it is not armed until the archive's final location is known, and
  `note!` had only stderr — which a released build does not have. The outcome
  is now remembered and written as soon as there is somewhere to write it. The
  first run after a rename is exactly the run somebody would want a record of.
- **A mistake that cost the owner work, recorded because it should not happen
  twice.** The first rename script used PowerShell's `-replace`, which ignores
  case, so a rule written for `SLOBOT` also matched `Slobot` and turned the
  product name into `VOLOCAL` in all 36 files. Reverting it with
  `git checkout -- .` reverted *everything* uncommitted, including two NSIS
  installer bitmaps the owner had just redrawn with the new branding. They were
  never committed and are gone. The second script uses `-creplace` throughout
  and prints every line it would change before it writes anything.
- Files: 36 across the tree, plus `src-tauri/tauri.conf.json` (identifier) and
  `src-tauri/src/main.rs` (the move and its tests).
- Verified: `npm run build`; `npm run test` (65); `cargo fmt --check`;

### 2026-08-10 — A release candidate now has to prove more than a green build

- Closes package 5 of the hardening plan. CI already ran the real Vite build,
  the frontend tests, `cargo fmt`, `cargo clippy -D warnings` and `cargo test`
  on every push. Two things it did not do, both of them only about releases.
- **A dictionary rule that only a release has to pass.** `i18n:check` treats a
  translation whose Czech source has never been fingerprinted as a warning.
  That is right while a change is in progress: the fingerprint is recorded once
  somebody has actually compared the two, and forcing it earlier would only
  teach people to record it without looking. But that fingerprint is the sole
  thing the drift check compares against later, so a key without one can never
  be caught by a reworded source — it is invisible to the only guard the
  dictionary has. `node scripts/i18n.mjs check --strict` turns that one warning
  into an error, and the installer job runs it for tags.
- Deliberately narrow. The other two warnings — a key nobody uses yet, one text
  sitting under two keys — stay warnings in both modes. They are untidiness,
  not something a reader would meet, and there are 79 of the second kind: a
  release gate that is red for something nobody intends to fix is a gate
  everybody learns to ignore.
- **A smoke test of the installed copy.** Everything else in CI says the code
  compiles and bundles; none of it says the result runs. The step installs the
  NSIS package silently, starts it, and waits for `whisp.db` to appear. The
  archive is the signal rather than the window: it is created by the Rust side
  during `setup`, after the settings are read and the migrations have run, so
  its existence means the application got past the part that can fail on a
  machine that is not the one that built it. A resource left out of the bundle,
  an absent WebView2, a panic before the first window — all three look like a
  perfectly green build until somebody double-clicks.
- The archive is asserted absent rather than deleted first. On a fresh runner
  it cannot exist, and a leftover one would make the test pass without the
  application having done anything.
- Tested where it will run, not where it was written: installing with `/S`
  locally would have overwritten the owner's own installation and opened their
  real archive, so the installer job was dispatched by hand on a clean runner.
- **A release today would fail the strict check, and that is a true finding.**
  Seven English entries have no fingerprint: the five `detail.find.*` keys and
  the two `errors.download.*` messages added this morning with the download
  verification. All seven were read against their Czech and are faithful —
  `{at} z {total}` → `{at} of {total}` and so on — so the fix is one command,
  `node scripts/i18n.mjs approve en`. It is not run here because it writes to
  `src/locales/sources.json`, which is one of the three files the owner has
  uncommitted work in and which this plan does not touch.
- Files: `.github/workflows/check.yml`, `scripts/i18n.mjs`, `CONTRIBUTING.md`,
  `README.md`.
- Verified: `node scripts/i18n.mjs check` passes (exit 0) and `check --strict`
  fails on exactly the fingerprint warning (exit 1), both against the committed
  state in a separate worktree so the owner's uncommitted dictionary edits
  could not flatter the result; the workflow YAML parses and the installer job
