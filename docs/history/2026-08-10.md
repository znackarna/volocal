### 2026-08-10 — Correcting entry: the webview's access to the disk is closed after all

- Supersedes the entry below it, written earlier the same day, which concluded
  that narrowing `assetProtocol.scope` breaks playback and reverted it. It does
  not. The grant was in the right command and the wrong half of the journey.
- The cause, and it is one line of TypeScript. `resolvedPlaybackSource` in
  `player.tsx` opened with `if (!path.endsWith(".mp3")) return path` — a
  shortcut that saves an IPC round trip for recordings that need no converted
  proxy. So `playback_source`, described in that entry as "the one command
  every path the window plays comes through", is skipped by everything that is
  not an MP3. The grant sat in a command the failing case never called.
- Which is why the earlier A/B was consistent and still wrong: it was run on an
  MP4, so the scope was closed and nothing had opened it. The two explanations
  that entry ruled out — a copied scope, a race with `convertFileSrc` — were
  both correctly ruled out. The one it did not consider was that the command
  never ran.
- Changed: the shortcut is gone, so every recording asks. The backend already
  handed a non-MP3 straight back unchanged, so the answer is identical; what
  changes is that the file about to be played is opened for the webview first.
  A comment on each side says why the round trip is not waste.
- Changed: `assetProtocol.scope` is `[]`. The webview may read nothing until
  something is played, and then exactly that one file.
- Measured on the owner's own archive, both directions, because this file has
  now been wrong about it once. With the scope closed and the grant in place:
  an MP4 plays (0:28 of 10:34, pause button, waveform moving, blocks
  highlighting as it goes) and so does an MP3 through its cached M4A proxy —
  the log records `granting …paul_radomil_cz.mp4 -> Ok(())` and
  `granting …playback-cache\…m4a -> Ok(())`. With the grant deliberately
  withheld and nothing else touched, the same clicks leave the clock at 0:22
  and the play button unchanged. The scope is what blocks; the grant is what
  opens.
- What made the difference this time was one line of logging. Two rounds of
  clicking proved *that* playback did not start and said nothing about why; a
  `note!` in the grant proved the command was not being called at all, which is
  a different problem from the one being investigated. When an experiment keeps
  answering "no", check that it is being run.
- Files: `src/player.tsx`, `src-tauri/src/commands/detail.rs`,
  `src-tauri/tauri.conf.json`, `SECURITY.md`.
- Verified: `cargo fmt --all --check`; `cargo clippy --all-targets -- -D
  warnings` silent; `cargo test` (142 passed); `npm run build`; `npm run test`
  (16 passed); and the playback runs above against the real application.

### 2026-08-10 — Narrowing the webview's access to the disk breaks playback

**Superseded by the entry above; the conclusion here is wrong.** Kept because
the reasoning is what the correction had to get past.


- Attempted, measured, **reverted**. Nothing of it shipped, and the measurement
  is the point: it would have broken playback for everybody.
- What was tried, and it is the smaller of the two variants the plan offers:
  `assetProtocol.scope` from `["**"]` to `[]`, and `playback_source` — the one
  command every path the window plays comes through — calling
  `app.asset_protocol_scope().allow_file(path)` for the recording, and for the
  cached proxy when that is what it returns. The grant went in before any
  branch that can fail, so the player's own fallback to the original file when
  ffmpeg is missing would stay readable.
- It compiles, `cargo check --all-targets` is silent, and **it does not work**.
  Opening a transcript and pressing play leaves the clock at 0:00, the play
  button unchanged and the waveform empty.
- Proven rather than assumed, because a synthetic click failing to start audio
  would look exactly the same: the scope was put back to `["**"]`, the
  application rebuilt, and **the identical click sequence** run again. It
  played — 0:05 of 10:34, the pause button, the waveform drawn, the first block
  highlighted. So the difference is the scope and nothing else.
- Where the next attempt should start, because two obvious explanations are
  already ruled out. `Manager::asset_protocol_scope()` returns a `Scope` whose
  `inner` is an `Arc<ScopeInner>` with the allowed patterns behind a mutex, so
  it is the shared scope and not a copy — the grant does reach *a* scope. And
  the grant happens before the command returns, so it cannot be a race with
  `convertFileSrc`.
- What is left to check, in order: whether the asset protocol's request handler
  consults that same scope instance; and whether the match survives a Windows
  path — `allow_file` stores an escaped glob, the request arrives URL-encoded,
  and a drive letter with backslashes is exactly where such a comparison goes
  wrong. The dev console will say which; it names the refused request.
- Kept as it was: `["**"]` with `SECURITY.md` describing it accurately. A
  window that can read the disk is a real weakness and it is written down; a
  recording that will not play is a broken application.

### 2026-08-10 — The security documentation says what the code does

- `SECURITY.md` carried three claims the repository disproves. It said the
  webview has no Content Security Policy, and one has been in
  `tauri.conf.json` since 7 August. It said downloaded components are checked
  by neither checksum nor signature, and `download.rs` has computed a SHA-256
  during the write and refused a mismatch since 10 August. And it listed six
  pattern-matched catalogue entries including `sherpa`, which stopped being
  downloaded at all. `README.md` repeated the second one.
- Every concrete claim was read against the code rather than remembered. What
  replaces them is narrower, not warmer:
  - the verification machinery exists, but `EXPECTED_HASHES` is **empty**, so
    today nothing is compared for any component and HTTPS is still the whole
    guarantee. `installed.json` records `verified: false` rather than treating
    a file in the right place as evidence of where it came from — and nothing
    in the interface shows that record yet, which the document now says;
  - the policy is quoted in full and read directly. What it closes: remote
    script, style, font and image; `eval` and `new Function`; plugins; base
    rewriting; embedding; and the usual ways out — fetch, XHR, WebSocket, image
    beacon. What it does not: `style-src` carries `'unsafe-inline'` for React's
    style attribute, `window.location` is governed by none of it and
    `form-action` is unset, and a CSP says where content may be loaded from,
    not which Tauri commands running code may call. It is the second line of
    defence, not the first;
  - five entries are found by pattern, and `yt-dlp`'s fixed address points at
    `releases/latest`, so six are whatever their project publishes today. Until
    they are pinned, no digest can exist for them.
- Kept as admitted limits: the archive is unencrypted, the asset scope is still
  `["**"]` and the policy does not narrow it — `media-src` and `img-src` admit
  `asset:` explicitly — and the installer is unsigned. Added: the installer
  fetches the WebView2 runtime from Microsoft when the machine lacks it.
- Both language halves changed together and were compared marker by marker;
  every count matches, and `csp: null`, `verification_path` and `sherpa` are
  gone from both.
- `README.cs.md` gains a pre-release checklist item to re-read these claims
  against the code. The document carries the date it was last checked, so
  staleness is visible rather than assumed.
- Files: `SECURITY.md`, `README.md`, `README.cs.md`.
- Verified: `npm run build` passed, exit 0. Cargo was not re-run — no Rust file
  is touched — and CI runs both on the pull request.

### 2026-08-10 — Eight downloads are compared against a digest the publisher wrote

  was compared for any component and HTTPS was still the whole guarantee.
- Eight entries can be filled from the publishers themselves and are: Hugging
  Face serves an LFS file's SHA-256 as its object id, GitHub serves a release

  comment above the constant already warned about.
- The seven Hugging Face addresses move from `resolve/main` to
  `resolve/<revision>`, and that is the half that makes the other half true: a
  digest against a branch starts refusing the download the day the publisher
  pushes anything. The bytes are identical today, so nobody downloads anything
  different.
- Eight of sixteen, and the rest is not an oversight. `model-hlasy` predates
  GitHub's digest field and reads null; five components are found by matching a
  pattern over live releases; `yt-dlp` points at `releases/latest` and `ffmpeg`
  at a rolling build. None of those addresses names one artefact. Pinning them
  is the remaining half of that work and the version is the owner's choice.
- Three tests, each guarding a distinct way to get this silently wrong: a hash
  under an id that does not exist compares nothing and reads as verified; a
  hash on a pattern-matched component refuses every download; a hash beside a
  branch address does the same on the next push.
- Verified against the real network rather than only in the abstract: all ten

  downloaded and hashed here — `ggml-silero-v6.2.0.bin` and

### 2026-08-10 — The frontend gets its first automatic tests

  not close, the collapsing header, player state — were all in the interface.
- The first layer is logic that needs no DOM. `plain` and `changedWords` moved
  out of `Detail.tsx` into `src/transcriptText.ts` unchanged, and both are
  chosen for the same reason: they fail **quietly**. A broken `plain` makes the
  search find nothing; a broken `changedWords` underlines the wrong word.
  Neither raises anything.

  watching them pass: dropping the diacritic strip fails four, replacing the
  subsequence walk with a position-by-position compare fails three, restoring
  each returns to sixteen. The bundle is the same 495.71 kB, so the move cost
  nothing.
- `npm run test` is wired into `package.json` and into CI.
- One change to a guard rather than to the test: `i18n:check` no longer scans
  `*.test.ts(x)` for hardcoded text. A test of Czech text handling has to
  *contain* Czech text, and putting those strings in the dictionary would offer
  them for translation. The exclusion is narrow — it touches only the
  hardcoded-text scan, while `usedKeys` walks the tree itself, so a key
  referenced from a test still counts as used. Proven in both directions: the
  same literal in a component still fails with its file and line, in a test
  file it does not.

  editing a segment, a cancelled dialog) and the Windows smoke test. Both need

### 2026-08-10 — A robot proposes newer component versions every Monday

- The entry above closed a hole and opened a smaller one, which it said out
  loud: with every component pinned, a fix upstream no longer arrives on its
  own and somebody has to notice. This is that somebody — and it writes down
  what it found rather than deciding.
- `src-tauri/components.json` now holds every address and digest, keyed by the
  id the catalogue already uses. Data rather than Rust for one reason: a script
  editing Rust source with a regular expression is the shape that has already
  silently replaced the wrong thing in this repository once. `download.rs`
  embeds it with `include_str!` and parses it once.
- **The one rule, and the whole value of the thing:** the script copies a digest
  from the publisher — GitHub's release asset `digest`, a Hugging Face LFS
  object id, gyan.dev's published `.sha256` — and never computes one from a
  downloaded file, which would attest only that a file matches itself. Where a
  publisher offers none, the entry is left exactly as it was: a newer version
  nobody can verify is not an improvement.
- Each proposed address is requested before being written down, so a rename
  upstream cannot land a 404 in the catalogue and still look like a tidy pull
  request.
- The workflow opens a pull request and never pushes to `main`. Two components
  set `track: null` with a sentence saying why: `whisper-vulkan` is a third
  party's rebuild rather than an upstream release, and `model-hlasy` is a model
  in a release that is never reissued.
- Two tests guard the new seam: the pins parse and every digest is 64
  hexadecimal characters, and the catalogue and the pins name the same set **in
  both directions** — a pin nothing installs is dead weight, a component with no
  pin panics on first use.
- Verified against the real publishers both ways. Run as it stands, the robot
  reaches the same fourteen addresses and digests that were pinned by hand a few
  hours earlier and changes nothing, which is an independent check on that work.
  Rolled `deno` back two versions with a zeroed digest and it found v2.9.5,
  wrote the publisher's real digest, and reported one change; restoring returned
  it to zero.
- **What no robot can check, and the pull request it opens says so:** whether
  the new version works. A newer whisper.cpp can change a flag or an output
  shape, and nothing here runs a transcription.
- Worth knowing: a pull request opened with `GITHUB_TOKEN` does not trigger
  other workflows, by GitHub's own design against loops. `Checks` therefore does
  not start on the robot's pull request by itself; closing and reopening it
  starts them.
