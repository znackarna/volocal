### 2026-08-12 — An archive from a newer version is refused, not guessed at

The failure of 1.0.5 had two halves. The leftover tables were fixed in 1.0.6;
this is the other half, and it is the one that would have mattered more.

When 1.0.4 opened an archive 1.0.5 had migrated, it looked for `nahravky`, did
not find it, and its `CREATE TABLE IF NOT EXISTS` made an empty one. What saved
the owner from a worse morning is that the *next* start crashed. Had it not, the
application would have opened cheerfully and shown an archive with nothing in
it — no recordings, no transcripts — while every word was still on the disk.
That is the worst thing this application could tell somebody who has lost
nothing.

- The archive now carries the schema it was written for, in the settings table,
  written last so it only ever claims a schema it actually reached.
- `open` reads it before it renames or creates anything. A number higher than
  this build knows is `ArchiveFromTheFuture`, and the archive is returned
  untouched.
- The startup dialog tells the two cases apart, because they ask for opposite
  actions. A damaged archive wants a backup copied over it. This one wants
  nothing done to it at all: *"Aktualizujte Volocal… S archivem nic nedělejte —
  je v pořádku a nic v něm nechybí."* Telling its owner to copy a backup over a
  perfectly good archive is the one instruction here that could actually destroy
  work.
- It cannot reach the builds already installed. It stops the next migration from
  repeating this one.
- One thing worth remembering from writing it: `klice` keeps its value in
  `hodnota` and `settings` in `value`, and this runs *before* the rename. Asking
  for the wrong one is not a missing row that `optional()` absorbs — it is a
  missing column, and it fails. The pair is now chosen together.
- Three tests: that opening writes the number down, that a higher number is
  refused by name and the archive left exactly as it was, and that an archive
  with no number is opened normally and given one.
- Files: `src-tauri/src/db.rs`, `src-tauri/src/main.rs`.
- Verified: `cargo test` (160), `clippy -D warnings`, `fmt`, `npm run build`.

### 2026-08-12 — The Dependabot alert, and why it was dismissed rather than fixed

Alert 6: unsoundness in `glib`'s `VariantStrIter`, fixed in 0.20.0, and this
project has 0.18.5 in `Cargo.lock`.

It is dismissed as not used, on evidence rather than on a shrug:

- `cargo tree --target all -i glib` shows it arriving through `gtk`, `gdk`,
  `webkit2gtk` and `wry` — the Linux webview stack.
- `cargo tree --target x86_64-pc-windows-msvc -i glib` prints nothing. For the
  only target Volocal ships, it is not in the dependency graph and never
  compiled into anything released.
- `cargo update -p glib` locks 0 packages: 0.18 is what the gtk-rs versions
  Tauri pins require, so it cannot be moved without Tauri moving first.

Written down because a dismissed alert is exactly the kind of decision that gets
rediscovered later as a mystery. If Volocal is ever built for Linux, this stops
being true and the alert should be reopened.

### 2026-08-12 — A way back from a backup, inside the application

The dialog that appeared when 1.0.5 could not open the archive printed a
procedure: save the file aside, copy the newest backup over it, rename it to
match the archive. It is sound advice and it was the only way back — work with a
file manager, at the one moment somebody is frightened, and the only place in
this application that asks for that.

Backups could be made and counted and their folder opened. The other half is
here now: a folded-away list of them by date and size, and a Restore beside each.

What `restore_backup` does, in the order it does it, because the order is the
whole thing:

1. The name is checked against the backup directory's own listing. A path
   arriving over IPC does not get to say which file may replace an archive.
2. The archive as it stands is copied aside as `whisp-before-restore.db`.
   Restoring is a decision somebody can regret within the minute — usually by
   picking the wrong date — and without this there is nothing to regret back to.
3. The open connection is replaced with one to `:memory:`, which closes the
   file. Windows will not replace an open file, and a half-copied archive is
   exactly the damage this exists to undo.
4. The backup is copied over and the write-ahead log removed with it: a `-wal`
   belonging to the old file would be replayed into the new one.
5. The archive is opened again through `open`, so a backup written by an older
   schema is migrated on the way in — and one from a newer build is refused by
   the guard added this morning rather than half-read.

The archive is reopened whether the copy worked or not. Leaving the application
holding `:memory:` would make every screen answer with an empty archive, which
is the lie this whole day has been about. The window reloads afterwards: what is
on every screen came from the archive that was just replaced.

Also: `SettingsDisclosure` can now be told when it is first opened, so the list
is fetched then rather than on every visit to the Files tab.

  `src/api.ts`, `src/Settings.tsx`, `src/css/04-nastaveni.css`, the dictionaries.

### 2026-08-12 — Renaming the archive is a one-way door, deliberately

The file rename has the failure the schema guard was built to stop, one level
lower: a build older than the rename does not find `whisp.db`, so it never opens
the archive, never reads the schema version the guard checks, and simply starts
an empty one. Observed rather than reasoned about — it happened to the owner's
own profile this afternoon, when a branch build renamed the archive and the
`main` build behind it made a fresh empty one beside it. Nothing was lost; the
4.7 MB file was sitting there under its new name.

Three ways out were put to the owner:

1. Leave it. Only somebody who goes back to an older version is affected, and
   since 1.0.5 that is already a one-way door because of the schema.
2. Leave a decoy: a `whisp.db` that is not a database, so an older build fails
   to open it and shows the dialog naming the backups — "I cannot open this"
   instead of an archive that is silently empty.
3. Do not rename at all.

His answer: nobody will run an older version. The application updates itself and
there is no reason to go back, so the case the decoy protects against is one
that does not happen outside a developer's working tree.

Recorded because the second option is the kind of idea somebody has again in six
months, and it was considered and declined for a reason, not overlooked.

### 2026-08-12 — The tools folder takes the application's own name

`%LOCALAPPDATA%\Whisp` was the last place carrying the first name, and looking
before moving changed the answer twice.

**It is not renamed to `Volocal`.** That folder exists: it is where the
installer puts the program and the uninstaller, 0.03 GB of it. Putting 20.79 GB
of models inside a folder an uninstaller owns is a folder an uninstall can
empty. The new name is `cz.znackarna.volocal` — the identifier, the same one the
archive's folder uses in the roaming profile, beside the program rather than
inside it.

**Twenty gigabytes do not move.** On one volume this is a directory rename: one
call, instant, and nothing can be half-copied.

- `tools_root` answers for both names — the new one if it is there, then the old
  one. A rename that could not happen, because a tool is still running out of
  `bin` and holds the folder open, means the models are found where they are
  rather than reported missing.
- The stored folder settings are the default `bin` and `models`, which are
  relative and travel with the root by themselves. Only an absolute path is
  looked at, and only when it starts with the folder that just moved: somebody
  who put their models on another drive chose that, and it is not ours to
  rewrite. Compared without case, because this is Windows.
- The folder to work in is passed in rather than read from the environment, so
  the tests can give it one that is not the machine's — `LOCALAPPDATA` is
  process-wide and these tests run beside each other.
- Seven tests: the rename with its contents, already-done, first-run, and the
  four ways a stored path can be affected or not.

Tried against a sandbox rather than the real 20 GB, which is the way the two
mistakes earlier today should have been made safe.

# Change log — 2026-08-12

### 2026-08-12 — Correcting entry: 1.0.8 pointed the application at a folder of browser cache

The tools folder migration shipped in 1.0.8 and could not work. Found within the
hour, by listing the folder before deleting anything from it.

`%LOCALAPPDATA%\cz.znackarna.volocal` is not ours alone. **WebView2 keeps its
profile there** — `EBWebView`, 252 MB on this machine — named after the same
identifier, and it puts it there the first time the window opens. So on every
machine that has ever run Volocal, that folder already exists.

Two things followed from asking only whether it exists:

- `rename_tools_root` refused: its target existed, so it returned without doing
  anything, on every machine.
- `tools_root` answered with it, because `is_dir()` was true. A folder holding a
  quarter of a gigabyte of browser cache and none of the tools. **Every model
  and every program reported missing** — the exact failure the comment in
  `tools.rs` warns about, three lines above where I wrote the bug.

**What makes a folder ours is that our things are in it**, not that it exists.
`holds_the_tools` asks for `bin` or `models`, and both the migration and the
lookup ask it now.

And the migration moves `bin` and `models` rather than the folder around them,
because that folder cannot be renamed onto a name WebView2 is already using.
Each is still a directory rename on one volume: instant, twenty gigabytes stay
where they are. The old folder is removed only if it is empty afterwards —
anything else in it is somebody else's.

Two tests hold it: a folder WebView2 made is not a folder of ours, and something
left in the old folder keeps it alive.

The lesson is the same one as the CSS classes and the status dots, in a third
costume: **existence is not identity.** A class that exists is not a class that
paints; a folder that exists is not a folder that holds your models.
