### 2026-08-11 — CI could not build the installer any more, and the first release goes out unsigned

- Dispatched the installer job on `main` before tagging anything, because the
  configuration had changed under it and nothing had built since. It failed:
  *A public key has been found, but no private key. Make sure to set
  `TAURI_SIGNING_PRIVATE_KEY`.* With a public key in the config the bundler
  demands the matching private key at bundle time, and that key must not be on
  a runner — anybody who can push a workflow could then sign a release this
  application accepts.
- Fixed by building CI's installer with `createUpdaterArtifacts` turned off,
  through a partial config the CLI merges. What comes out of CI is a build that
  proves the code bundles and the result starts; a release anybody installs is
  built and signed by hand.
- The path was wrong on the first attempt — `--config tauri.ci.conf.json`
  resolves against the working directory, not the Tauri folder, so it has to be
  `src-tauri/tauri.ci.conf.json`. Found in thirty seconds locally rather than
  in twenty minutes on a runner, and worth the habit: the failure is immediate
  and unmistakable, so it is cheap to provoke on purpose.
- Timing worth recording: this was found **before** the first tag existed. A
  tag is created the moment a draft release is published, so the failure would
  otherwise have appeared on the release itself.
- **The first release goes out unsigned, and that is a decision rather than an
  omission.** There is no code-signing certificate on the machine; `signtool`
  is installed and has nothing to sign with. The reason not to buy one today is
  that it would not help: OV certificates and the cheap cloud signing services
  start with no SmartScreen reputation and earn it by being downloaded, which
  is the thing that has not happened. Only EV is trusted on sight, at hundreds
  of dollars a year and a hardware token.
- So `release.ps1` grew `-Unsigned`. It has to be asked for — the guard exists
  to stop an unsigned release happening by accident — and it prints what every
  reader will see. Both paths tested: without the switch it stops, with it the
  run continues.
- Also cleared a warning the release build printed: `App.tsx` loaded the
  updater plugin behind `await import(...)`, which looked like it kept the
  module out of the bundle until somebody turned the check on. It did not — the
  About page imports the same module directly, so it was in the main chunk
  anyway, and the bundler said so. Now imported plainly, renamed to
  `checkForUpdate` because `check` is already the tool-availability state in
  that component.
- Files: `.github/workflows/check.yml`, `src-tauri/tauri.ci.conf.json`,
  `scripts/release.ps1`, `src/App.tsx`, `README.cs.md`.
- Verified: the config override loads (build reaches `beforeBuildCommand`);
  both `-Unsigned` paths; `npm run build` with the warning gone; `npm run test`
  (65).

### 2026-08-11 — Volocal 1.0.0, and a signing key that is worth something

- The version goes 0.9.0 to 1.0.0. Not a milestone awarded for effort: the
  number is a message to whoever is about to install it, and `0.9` was telling
  them to wait for something that had already arrived. The application is in
  daily use by its author on real work, and the hardening plan finished the day
  before.
- What 1.0.0 does not claim: that the installer is signed by anyone Windows
  recognises, or that an update has ever been installed by anything. Those are
  release-process gaps and the version makes no promise about them.
- The updater signing key was replaced first, with one that has a password.
  Today that costs nothing — nothing has been released, so no installation has
  the old public half. After the first release it costs everything: the public
  key is baked into every copy, and rotating it means none of them will ever
  accept an update again. It was the last cheap moment.
- The old key was generated without a password because the tool defaulted that
  way and it was convenient; anyone who could read the owner's profile could
  have signed an update the application would have accepted. Checked rather
  than assumed that the new one is different: signing with an empty password
  now fails with *Wrong password for that key*. The key id in the config
  changed from `8B3B0235CC530786` to `A2ECEAED4E1E4E1D`, and matches the public
  half on disk byte for byte.
- Files: `src-tauri/tauri.conf.json` (public key and version), `Cargo.toml`,
  `package.json`, `Cargo.lock`.
- Verified: `npm run build`; `npm run test` (65); `cargo test` (150);
  `i18n check --strict` exits 0.

### 2026-08-11 — "You have the newest version" belongs in the notice bar

- The owner's note after the first release: the answer to a check that found
  nothing should appear where the application says everything else, not under
  the button that asked.
- So the rule is now about whether anything can be done with the answer. A
  finished check with no follow-up — nothing newer, or it could not be reached

  that renders nothing is not a state.
- Corrected a comment while there, which had quietly become false: the file

### 2026-08-11 — Volocal 1.0.1, released to find out whether updating works

- Same application as 1.0.0. The point of it is the one thing no amount of
  reading proves: that an installed copy fetches the feed, accepts the
  signature, downloads the installer and comes back running. Until a second
  release exists there is nothing to update *to*, so the loop cannot be
  exercised at all.
- What 1.0.0 already proved, by being pressed: the feed is fetched, parsed and
  compared. That much works.
- The build no longer needs the signing key. The bundler's own `.sig` was
  always thrown away — it is made over bytes Authenticode has not touched yet,
  and the signature that ships is made in the second pass over the file as it
  will be downloaded. So the twenty-minute step now builds with the updater
  artifact turned off, exactly as CI does, and asks for no password. Only
  publishing needs the key.
- Files: version in all four, `scripts/release.ps1`.


### 2026-08-11 — A release went out carrying the previous version's installer

- Reported from the running application: the update downloads, the application
  closes, and nothing installs. Everything about that behaviour was correct;
  the contents were not. `v1.0.1` held `Volocal_1.0.0_x64-setup.exe`, and
  `latest.json` pointed at it while claiming version 1.0.1. The application
  downloaded itself and the installer had nothing to do.
- How it got there. The 1.0.1 build failed on `npm run tauri build --
  --config …` — **npm claims `--config` for itself even after `--`**, the same
  trap as `-w` earlier the same night, and reports `Unknown cli flag`. The
  failure left the previous installer in the bundle folder, and the publishing
  pass picks the newest `.exe` there, which was then the 1.0.0 one.
- Both halves fixed. The build calls `node_modules\.bin\tauri.cmd` directly
  rather than through npm, which is what does the flag-grabbing — and the same
  line in CI was corrected, where it had additionally kept a path that does not
  resolve. And the publishing pass now refuses an installer whose name does not
  carry the version being released: *that is the previous build, still in the
  folder because this one did not get as far as replacing it.*
- Which is the shape of the whole evening's lesson again: the guard was written
  from the failure that had already happened, and checked against exactly the
  state that caused it before being trusted.
- The bad release and its tag were deleted rather than patched. Nobody but the
  owner had seen it, and a release whose assets were swapped underneath it is
  worse to reason about later than one that never existed.
- What this cost, and it is worth being plain: the update path was proven to
  work — download, exit, hand over to the installer — by a test that failed for
  a different reason. The half that still has not been seen is an installer
  that actually replaces the program and starts it again.
- Files: `scripts/release.ps1`, `.github/workflows/check.yml`.


### 2026-08-11 — The installer was being killed by the job object that keeps ffmpeg in line

- Reported twice, and the second time with the release finally correct: the
  update downloads, the progress bar fills, the window disappears — and nothing
  installs, nothing comes back.
- Found by elimination rather than by reading. The release was correct. The
  installer *was* written to `%TEMP%`, four copies of it, one per attempt. Run
  by hand with the plugin's own arguments — `/P /R /UPDATE` — it installed
  1.0.1 and restarted the application. Called through `ShellExecuteW` exactly
  as the plugin calls it, it worked. Called with the application still running,
  it worked. Every part worked in isolation.
- What was left was the one thing the plugin does that no test of mine did:
  `std::process::exit(0)` immediately afterwards. And this application puts
  itself in a **job object** with `KILL_ON_JOB_CLOSE`, so that whisper, ffmpeg
  and llama-server cannot outlive the window. The installer is started by this
  process, joins the same job, and is killed the instant the window exits. The
  safeguard was working perfectly on the one process that had to be exempt.
- `let_the_installer_out` adds `SILENT_BREAKAWAY_OK` to the job, and the window
  calls it immediately before `downloadAndInstall`. Added rather than replacing
  the kill flag, so everything already running still dies with the window; only
  what starts after the call — the installer — is left out.
- A detour worth writing down: the command would not compile in `main.rs`
  at all. `#[tauri::command]` in a binary's crate root collides with itself
  through `generate_handler!` — *`__cmd__…` is defined multiple times* — with
  one definition in the file. Every other command in this codebase lives in
  `commands/`, and that is not decoration.
- Files: `src-tauri/src/main.rs`, `src-tauri/src/commands/updates.rs` (new),
  `src/settings/updates.tsx`, `src/api.ts`, the dictionaries.
