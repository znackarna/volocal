### 2026-08-11 — CI could not build the installer any more, and the first release goes out unsigned

- Dispatched the installer job on `main` before tagging anything, because the
  configuration had changed under it and nothing had built since. It failed:
  *A public key has been found, but no private key. Make sure to set
  `TAURI_SIGNING_PRIVATE_KEY`.* With a public key in the config the bundler
  demands the matching private key at bundle time, and that key must not be on
  a runner — anybody who can push a workflow could then sign a release this
  application accepts.
- Fixed by building CI's installer with `createUpdaterArtifacts` turned off,
  through a partial config the CLI merges. What comes out of CI is a build that
  proves the code bundles and the result starts; a release anybody installs is
  built and signed by hand.
- The path was wrong on the first attempt — `--config tauri.ci.conf.json`
  resolves against the working directory, not the Tauri folder, so it has to be
  `src-tauri/tauri.ci.conf.json`. Found in thirty seconds locally rather than
  in twenty minutes on a runner, and worth the habit: the failure is immediate
  and unmistakable, so it is cheap to provoke on purpose.
- Timing worth recording: this was found **before** the first tag existed. A
  tag is created the moment a draft release is published, so the failure would
  otherwise have appeared on the release itself.
- **The first release goes out unsigned, and that is a decision rather than an
  omission.** There is no code-signing certificate on the machine; `signtool`
  is installed and has nothing to sign with. The reason not to buy one today is
  that it would not help: OV certificates and the cheap cloud signing services
  start with no SmartScreen reputation and earn it by being downloaded, which
  is the thing that has not happened. Only EV is trusted on sight, at hundreds
  of dollars a year and a hardware token.
- So `release.ps1` grew `-Unsigned`. It has to be asked for — the guard exists
  to stop an unsigned release happening by accident — and it prints what every
  reader will see. Both paths tested: without the switch it stops, with it the
  run continues.
- Also cleared a warning the release build printed: `App.tsx` loaded the
  updater plugin behind `await import(...)`, which looked like it kept the
  module out of the bundle until somebody turned the check on. It did not — the
  About page imports the same module directly, so it was in the main chunk
  anyway, and the bundler said so. Now imported plainly, renamed to
  `checkForUpdate` because `check` is already the tool-availability state in
  that component.
- Files: `.github/workflows/check.yml`, `src-tauri/tauri.ci.conf.json`,
  `scripts/release.ps1`, `src/App.tsx`, `README.cs.md`.
- Verified: the config override loads (build reaches `beforeBuildCommand`);
  both `-Unsigned` paths; `npm run build` with the warning gone; `npm run test`
  (65).

### 2026-08-11 — A release went out carrying the previous version's installer

- Reported from the running application: the update downloads, the application
  closes, and nothing installs. Everything about that behaviour was correct;
  the contents were not. `v1.0.1` held `Volocal_1.0.0_x64-setup.exe`, and
  `latest.json` pointed at it while claiming version 1.0.1. The application
  downloaded itself and the installer had nothing to do.
- How it got there. The 1.0.1 build failed on `npm run tauri build --
  --config …` — **npm claims `--config` for itself even after `--`**, the same
  trap as `-w` earlier the same night, and reports `Unknown cli flag`. The
  failure left the previous installer in the bundle folder, and the publishing
  pass picks the newest `.exe` there, which was then the 1.0.0 one.
- Both halves fixed. The build calls `node_modules\.bin\tauri.cmd` directly
  rather than through npm, which is what does the flag-grabbing — and the same
  line in CI was corrected, where it had additionally kept a path that does not
  resolve. And the publishing pass now refuses an installer whose name does not
  carry the version being released: *that is the previous build, still in the
  folder because this one did not get as far as replacing it.*
- Which is the shape of the whole evening's lesson again: the guard was written
  from the failure that had already happened, and checked against exactly the
  state that caused it before being trusted.
- The bad release and its tag were deleted rather than patched. Nobody but the
  owner had seen it, and a release whose assets were swapped underneath it is
  worse to reason about later than one that never existed.
- What this cost, and it is worth being plain: the update path was proven to
  work — download, exit, hand over to the installer — by a test that failed for
  a different reason. The half that still has not been seen is an installer
  that actually replaces the program and starts it again.
- Files: `scripts/release.ps1`, `.github/workflows/check.yml`.


### 2026-08-11 — The installer was being killed by the job object that keeps ffmpeg in line

- Reported twice, and the second time with the release finally correct: the
  update downloads, the progress bar fills, the window disappears — and nothing
  installs, nothing comes back.
- Found by elimination rather than by reading. The release was correct. The
  installer *was* written to `%TEMP%`, four copies of it, one per attempt. Run
  by hand with the plugin's own arguments — `/P /R /UPDATE` — it installed
  1.0.1 and restarted the application. Called through `ShellExecuteW` exactly
  as the plugin calls it, it worked. Called with the application still running,
  it worked. Every part worked in isolation.
- What was left was the one thing the plugin does that no test of mine did:
  `std::process::exit(0)` immediately afterwards. And this application puts
  itself in a **job object** with `KILL_ON_JOB_CLOSE`, so that whisper, ffmpeg
  and llama-server cannot outlive the window. The installer is started by this
  process, joins the same job, and is killed the instant the window exits. The
  safeguard was working perfectly on the one process that had to be exempt.
- `let_the_installer_out` adds `SILENT_BREAKAWAY_OK` to the job, and the window
  calls it immediately before `downloadAndInstall`. Added rather than replacing
  the kill flag, so everything already running still dies with the window; only
  what starts after the call — the installer — is left out.
- A detour worth writing down: the command would not compile in `main.rs`
  at all. `#[tauri::command]` in a binary's crate root collides with itself
  through `generate_handler!` — *`__cmd__…` is defined multiple times* — with
  one definition in the file. Every other command in this codebase lives in
  `commands/`, and that is not decoration.
- Files: `src-tauri/src/main.rs`, `src-tauri/src/commands/updates.rs` (new),
  `src/settings/updates.tsx`, `src/api.ts`, the dictionaries.

### 2026-08-11 — An update says what is in it, before anybody agrees to it

  whether to restart their work; what they want is what improves. The detail is
  not lost, it is in the English text and in this file.

  in the settings panel: it is a question with an answer, and a dialog is what
  this application asks questions with. It opens itself when a check finds a

  up to and including 1.0.4 is such a release.

### 2026-08-11 — The code speaks English

Half the names in this application were Czech: the CSS custom properties, some
250 of the 433 class names, and a handful of identifiers. The interface stays
Czech — that rule is unchanged, and the dictionaries were not touched. This is
about the names the people building it read.

Done in three commits, each by a script that measures the shape before and
after and refuses to write when they differ. Nothing here changes a pixel, and
that is exactly why it needs proving: an undefined custom property or class does
not fail, it silently drops what used it.

- **Custom properties.** 964 mentions before and after, 54 defined, 54 used, the
  same single name used without a definition. `--zaves` became `--scrim`,
  `--radek-znacka` `--row-thumb`, `--listek` `--note` — named for what they do
  where translating the word would have said less.
- **Classes.** 1326 mentions, 433 defined, 433 used, 9 dangling — all unchanged.

Three traps, each of which a search and replace would have walked into:

1. **Two classes renamed onto one name still count correctly.** `.segment.aktivni`
   becoming `.segment.active` would begin matching anything carrying `segment`
   and `active` for reasons of its own. Seven were heading that way; all seven
   were given names of their own. Consolidating that vocabulary is a real
   improvement and a different change from this one.
2. **A pass over every word in every string rewrites the dictionary.** `ne` is a
   class here and the Czech for "not": `„Seznam", ne „archiv"` in a translator's
   note came out as `no`.
3. **A string inside a `className` is not always a class.** `tab === "summary" ?
   "active" : ""` holds one of each, and the worse mistake is the other one — a
   recording's stored status is compared this way, and renaming
   `status === "hotova"` would have stopped matching anything the database has
   written since the first release.

And three the script could not see, found by reading afterwards: `className:
"hotovo"` as an object property rather than a JSX attribute, and
`querySelector<HTMLElement>(".detail-jmeno")` and `.closest<HTMLElement>(".slovo")`
— a type parameter between the name and the bracket, which the pattern for
`querySelector(".x")` did not allow. All three had lost their styling silently.
The lesson is the one the whole exercise is about: the checks prove what they
measure, and reading is what finds the rest.

Identifiers: `nadpis` → `title`, `nicive` → `destructive`, `onZavri` → `onClose`
in the confirmation dialog and its four callers; two locals in Settings and

### 2026-08-11 — The schema stopped being Czech, and every archive comes with it

The last of the Czech names: `nahravky`, `segmenty`, `mluvci`, `zacatek`. Unlike
the classes and the tokens, these are on people's disks, so this is not a rename
but a migration.

**Names.** Every Czech token has exactly one English counterpart, which is what
made a mechanical pass possible at all. Two choices were forced. `nazev` is a
recording's and a folder's and both became `name`, though the struct calls the
first a title. And `konec` could not become `end`: END is a keyword in SQLite and
an unquoted column of that name breaks inside an expression — hence `start_time`
and `end_time`, named as a pair so the reason shows at both.

**What is not renamed.** The values. `stav` is a column and `'chyba'` is one of
the four things it has ever held; every archive on disk says so, and the Rust
that writes it passes `"chyba"` by hand. The column moved, what it says did not.

**Scope, after getting it wrong twice.** The first pass renamed matching tokens
in every Rust file, and reached where a schema has no business being: a Czech
comment became `name rodiny`, a line the application writes into a portable copy
promised the reader it would `všechno search u sebe`, and a local in the WAV
header reader called `body` turned into `points`. All of it compiled — only two
calls colliding with a method name failed. The second pass renamed inside Rust
string literals found by pattern, and went out of phase: one mis-parsed literal
pairs a closing quote with the next opening one, and from there a whole query
looks like prose. It skipped one silently. What worked is the dull rule — the two
files that hold SQL, and in them the lines that are not comments.

**The migration.** `rename_schema_to_english` runs before the `CREATE TABLE IF
NOT EXISTS` batch, and has to: those statements name the English tables, so an
archive left in Czech would end up with both — the reader's recordings in one set
and an empty set beside them, with the application reading the empty one.

- `PRAGMA foreign_keys` is switched on first, outside the transaction where it
  can still take effect. With it off, SQLite renames the table and leaves every
  `REFERENCES nahravky(id)` pointing at a name that no longer exists.
- The full-text index is dropped rather than renamed — `ALTER TABLE RENAME
  COLUMN` does not work on a virtual table — and rebuilt from the segments after
  the batch, so searching a transcript written last week still finds it.
- A copy of the archive is taken first, with `VACUUM INTO` rather than a file
  copy: the write-ahead log may hold the last session's work, and copying the
  main file alone would leave it out of the very backup meant to protect it. It
  lands beside the archive as `whisp-before-english.db`. This is the first
  migration an older build cannot read past — it would look for `nahravky` and
  make an empty one — so it is the first that leaves a way back.

**Verified.** Three tests over an archive written out as 1.0.4 wrote it, byte for
byte rather than built from the current schema — a fixture derived from the code
under test follows it wherever it goes and proves nothing. They check that the
recording, segment, speaker, note and dictionary entry all survive; that the
status value is still `hotova`; that the search index was rebuilt; that
`ON DELETE CASCADE` still holds, which it only does when the rename saw the
foreign keys; that a second open does nothing; and that the copy left behind is
still readable Czech. 155 tests, `clippy -D warnings`, `fmt`, `npm run build`.

### 2026-08-11 — Something to hand over when it goes wrong

The gap this closes was measured, not imagined. Speech detection came up
switched off after an install; the only evidence was a sentence describing it,
and the stored settings were read hours later, after they had already been put
right. What was missing was not a feature but a way to hand the state over.

- `diagnostic_report` builds one block of plain text: version, operating system,
  whether the copy is portable, where the archive and the log are; the model,
  the compute that was actually chosen against the one that was asked for, the
  NVIDIA driver, speech detection and its threshold, speakers and the clustering
  value, beam, threads, entropy; the ten components with the paths they were
  found at; and the last sixty lines of the log.
- Assembled in Rust rather than in the window, because this is the side that can
  see the settings as stored, the tools as found, and the log at all.
- The button sits under the component list in *Technické podrobnosti*, which
  until now could be read and not taken: that list answers "is it there", and a
  problem usually needs "and what was it doing".
- Nothing is sent anywhere — it goes to the clipboard and the person decides.
  Which is also why the report carries no file names from the archive and no
  transcript text. Paths to the tools are in it, because a wrong path is half of
  what goes wrong; a path can name the account the machine is logged in as, and
  that is the most personal thing in there. The note under the button says so.
- The clipboard is `copyPlainText`, already written for the transcript, with its
  selection-based fallback for the WebView builds that expose the API and refuse
  it. A refusal gets its own message naming the log file, so there is a second
  way even then.
- Files: `src-tauri/src/commands/settings.rs`, `src-tauri/src/diagnostics.rs`,
  `src-tauri/src/main.rs`, `src/Settings.tsx`, `src/api.ts`,
  `src/css/04-nastaveni.css`, the dictionaries.
- Verified: `cargo clippy -D warnings`; `cargo test` (155); `npm run build`;
  `npm run test` (77); `i18n check --strict`.

### 2026-08-11 — The player has tests

It had none, and the hardest defect in this project lived there: clicking a word
at 39:07 in an MP3 started playback eight seconds late. The fix — a converted
M4A proxy, one conversion per recording however often it is asked for, and a
waveform that keeps being asked for while ffmpeg is still working — was held up
by nothing but somebody remembering it.

Eleven tests over the part that can be tested without a canvas or an audio
device:

- **Joining.** Asking twice starts one conversion; a different source path for
  the same recording is a different conversion, because changing a path
  invalidates the proxy; and a failure is not remembered, so the next press
  tries again. Without that last one, a single failed conversion left the
  recording unplayable until the application was restarted.
- **Polling.** A waveform that is ready is handed over with nothing polled;
  while ffmpeg is still working it asks again; navigating away stops it between
  attempts rather than running the full three minutes; a backend error ends it.
- **The equalizer.** A moment between two frames is read from both; before the
  beginning and past the end it stays inside the data; a recording with no
  equalizer gives an empty list rather than throwing; and it resamples for a
  wider or narrower player.

The module is imported freshly for each test, because the join table is module
state and a test inheriting it from the one before would pass for the wrong
reason.

Both mutations bite: removing the join makes "asking twice starts one
conversion" fail, and keeping a failed promise in the table makes "a failure is
not remembered" fail. Checked by making each change and watching the test go
red, then putting it back.

- Verified: `npm run test` — 88, up from 77.

### 2026-08-11 — The duplicate-text warning was made to mean something

Seventy-nine came up on every run, and had for months. Three unrelated things
were in that heap: Czech plural forms that are identical on purpose, one
question asked from two screens, and words that merely met by accident. A
warning that is always there is not a warning — and this one made the real
problem invisible.

The real problem is drift: the same Czech sentence translated two different
ways, or translated in one place and forgotten in the other. A reader can see
that — the same button worded differently depending on where they opened it —
and it cannot happen without somebody having edited one and not the other.

The check now reports exactly that, and says the seventy-nine as a number rather
than a list. It found eight, of which five were real:

- `Přepis nahrávky {title} bude smazán…` had "The transcript of {title}" in one
  place and "The transcript of the recording {title}" in the other.
- The same for `Text i ruční úpravy u nahrávky {title}…`.
- `Připravuji jazykový model`, `Připravuji shrnutí` and `Připravuji překlad` each
  had a version with the article and one without.

All five unified. The three that are left are not defects but a copy question,
and they are worth putting to the owner rather than papering over: `Přepis` is
`Transcript` on the preview tab and `Transcription` as a settings tab; `Nový
záznam` is `New recording` at the microphone and `New entry` in the dictionary;
`Umístění` is `Locations` for folders and `Location` for one. Each pair is
genuinely two different things — which means the Czech word is doing two jobs,
and only its author can say whether that is worth fixing.

- Files: `scripts/i18n.mjs`, `src/locales/en/app.ts`, `src/locales/en/detail.ts`.
- Verified: `i18n check --strict`; `npm run build`.
