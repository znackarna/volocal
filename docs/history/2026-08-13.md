### 2026-08-13 — Two clicks on *Zálohovat teď* in one second reported a broken archive

Found by pressing the button quickly in the running application:

```
output file already exists: Error code 1: SQL error or missing database
```

Nothing was broken. The stamp in a backup's name is accurate to the second —
`volocal-2026-08-13-004512.db` — and the button re-enables the moment the first
copy is written, so a second click inside the same second aims at a name that is
already taken. `VACUUM INTO` refuses to overwrite, and its refusal arrived on
screen wearing the words *SQL error or missing database*, which is the last
sentence anybody should read about an archive that is perfectly fine.

Fixed where the name is made, not where the copy is written: if a file for this
second is already there, it is the copy this call would have made, and it is
returned. What was asked for is a backup of now, and there is one.

Two fixes deliberately not made:

- **Widening the stamp.** `backup_stamp` parses exactly `0000-00-00-000000`,
  `list_backups` orders by that text, and the rotation reads the day out of it.
  Every backup already written on every machine is in that shape.
- **Overwriting.** `back_up`'s own comment says it refuses to clobber so that a
  timestamped name can never land on an older copy. That is worth keeping, and
  this case is the one time the name is not an older copy's.

- Files: `src-tauri/src/db.rs`.

the newest copy whatever the time — passes the first test and quietly stops

### 2026-08-13 — Correcting entry: the prompts are not the thing that is wrong

The entry above left the Czech prompts in `ai_edit.rs` as an open question,
because `ARCHITECTURE.md` says prompts stay English. Asked whether the switch
was necessary — an English prompt being fine if it reaches the same result —
the answer turned out to be written down already, on 3 August:

> Fixed: an English transcript came back in Czech from *Vylepšit přepis*. The
> instructions in `system_prompt` are written in Czech and opened with `Jsi
> pečlivý český editor`, so the model answered in the language it was addressed
> in. […] The instructions stay in Czech, because they were tuned against Czech
> transcripts and their examples are Czech; only the language of the answer is
> now pinned to the language of the input.

*If it reaches the same result* is exactly the condition, and this project has
already measured the prompt's language changing the result — not on a large
hosted model but on the small local one that actually runs here. Two further
things hold the decision up. The examples are Czech grammar: in `Mně se líbí,
když se setkáte s lidmi` the model must keep `setkáte` rather than `setkám`,
and there is no English sentence that demonstrates it, so an "English prompt"
would be a mixed one anyway. And the rule against translating opens and closes
the prompt precisely because the instructions are in a different language from
the input — that defence exists because the failure happened.

So the document was the wrong half. `ARCHITECTURE.md` stated a rule with no
exception while the exception was older than the sentence and had a fixed bug
behind it. It now names the exception, gives the one-line reason, and points at
the day. Anybody who wants English prompts still can — as a measured
experiment, the same recording through both and read side by side, which is a
different kind of work from tidying.

- Files: `ARCHITECTURE.md`.
- Verified: `docs:check` and `i18n:check` clean. No code changed, so nothing
  else could.

### 2026-08-13 — The last Czech in stored data: four status values

Tables and columns stopped being Czech at schema 2, in 1.0.5. The four values of
`recordings.status` did not, because they are data rather than structure, and
renaming data means touching every archive that exists. They are `new`,
`transcribing`, `done` and `error` now, at schema 3.

**What makes it safe is not the `UPDATE`.** That is one statement over one
column, idempotent by construction — nothing maps onto a Czech value, so a
second run matches no rows. What makes it safe is `SCHEMA_VERSION` going to 3:
a build older than this refuses the archive by name, the way 1.0.5's guard was
built to, instead of reading it and finding every recording in a status it does
not know. The door was already one-way — [12 August](2026-08-12.md) put that to
the owner and his answer was that nobody runs an older version.

No copy is taken first, unlike the table rename. That one restructured the file;
this rewrites four known strings, and the backups the application already keeps
are the way back if one is ever wanted.

**The literals became `db::status`.** Thirty of them across eight files, and the
reason is that this rename is exactly the kind a compiler does not help with: a
status is a string in the SQL, in Rust, and on the far side of the IPC boundary,
so a missed one goes on compiling and simply stops matching. It has happened
here — `.hotova` became `.done` in the stylesheet in 1.0.5 and every status dot
in the archive went grey, with nothing failing anywhere.

The SQL still writes them literally, because a query is text. What holds the two
together is that the recovery tests now *insert* through the constant: change
`TRANSCRIBING` without changing `recover_interrupted`'s `WHERE`, and the row
stops matching and the test fails.

**Three tests failed on the first run, and all three were right to.** Two were
the schema number. The third was `layout_upgrade_rebuilds_existing_segments_once`
— its fixture writes `hotova` and
`completed_recording_ids_with_segments` now looks for `done`, so the upgrade
found nothing. That is precisely the silent-mismatch failure this change is
about, caught by a test that existed already.

On the frontend, `STATUS_CLASS` keeps its shape rather than collapsing into an
identity map: the stylesheet is free to call a class what it likes — `error` is
painted by `.failed` — and the map is the one place the stored value and the
class name meet. A new test pins the other direction: `statusClass("hotova")`
returns no class rather than a wrong one.
