# 2026-10-08

### 2026-10-08 — The window and the command line, side by side without harm

Four findings of the 1.3.0 release review (2026-10-05), all about a window
and `volocal-cli` working at the same time, fixed before the release at the
owner's word. Nobody who uses only the window sees any of it.

**Two command lines started together waited for each other for ever.** Each
held its lock and waited while any other lock existed. The busy check at the
start did not stop the second, because a row is marked as transcribing only
after the file has been imported, which takes seconds. Now a run waits only
for runs whose lock was taken before its own (`run_lock::held_before`, by the
lock file's creation time from the folder listing, ties by id), so they queue
in the order they arrived.

**Starting the window deleted a running command line's working files.** The
start-up sweep removed `%TEMP%\whisp` and `whisp-speakers` whole, and the
command line works in `<folder>\<id>` there too; closed files went, so a run
lost its converted audio and with it the speakers or the second language,
without saying so. `clear_leftover_temporary` now keeps the subfolders of the
recordings the start already knows are running elsewhere.

**The window did not wait for a command line on the same recording.** Its
queue skipped the lock with its own id — right for the command line, which
must not wait for itself, wrong for the window, which holds no run lock. And
its busy check read only the row, which says `done` for a moment between the
command line's phases. The window now waits for every lock (`waits_for`), and
starting a transcription, a transcription in another language, speakers or
a second-language fill refuses while the command line holds that recording
(`folders::worked_on`).

**A row left on "transcribing" by a crash stopped the command line for
good**, with a message telling the person to wait for a transcription that
did not exist; only starting the window cleared it. The window now holds a
file of its own while it is open (`running\window.open`, same rule as the run
locks, never mistaken for one). The command line reads a marked row as alive
only when a command line holds it or the window is open; otherwise it is a
leftover, cleared by the window's own rule (`recover_interrupted`: a
transcript means done, none means failed), and the run goes ahead.

Also: `docs/cli.md` (generated, from the help's introduction) and both
READMEs say where the command line is installed and how to start it, since
the folder is not on `PATH`.

Verified: `cargo test` 331 + 27 (new: queue order, a run without a lock, the
window's presence, the window waiting for the same recording, two command
lines queueing, the sweep keeping a live run's folder, a leftover cleared, a
held run and an open window each left alone); clippy and fmt clean;
`npm run build`, `npm test` (339), `docs-check`.
