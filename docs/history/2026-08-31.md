the page came back into the repository.

The kept row of each duplicated pair is the one naming that day file's own
first entry, which is what the rest of the table does and is checkable rather

**And the check is in `docs-check.mjs`, which `npm run build` already runs**, so
this cannot drift again quietly: every day file must have exactly one row, the
count must match, a row may not name a file that is not there, and the rows
must be in date order. Headings inside code fences are not counted — a heading
in an example is not an entry. Proved by running it against the index as it
stood before the repair: nine failures, one per fault.

The long paragraphs under *What each day was about* are deliberately left
alone. Two of them are duplicated as well — 20 and 21 August each have two,
and unlike the table rows they are not near-copies but different halves of the
same day — and point A1 says plainly that trimming them is the owner's call.
The check does not cover them, so that decision stays open rather than being
forced by a failing build.

### 2026-08-31 — Dependabot starts opening onto `dev`, and the three live bumps go in by hand

The reason its pull requests kept becoming ballast was one missing line.
`.github/dependabot.yml` named no `target-branch`, so it opened against the
default branch, which is `main` — the published branch, the one nobody commits
to. #214 sat there four days, and by the time it was read half of it was
bumping steps `dev` had already deleted.

`target-branch: dev` fixes that, and it has one cost worth writing down rather
than discovering: with it set, GitHub raises *security* updates only against
the default branch, so an advisory on an action will not arrive by itself. The
monthly run picks it up within the month. For four pinned actions that is the
trade worth making, and the alternative — pull requests nobody reads on a
branch nobody works on — was not protecting anything either.

**The three bumps that are still real were applied by hand**, so the pins are
current when `dev` next goes out: `checkout` 4.4.0 → 7.0.1, `setup-node`
4.4.0 → 7.0.0, `upload-artifact` 4.6.2 → 7.0.1. Every SHA was resolved from the
action's own tag before being written, not copied from the pull request.

The other three in #214 — `configure-pages`, `upload-pages-artifact` and
`deploy-pages` — are not applied and will not be: those steps left `site.yml`
when Pages was switched off on the 27th.

What was checked before applying them, because all three are major jumps:
`checkout` v7 refuses to check out a fork's pull request under
`pull_request_target` and `workflow_run`, and neither trigger is used here.
`setup-node` v5 began caching automatically when `package.json` carries a
`packageManager` field — it does not, and `cache: npm` is written out by hand
anyway, so nothing changes. `upload-artifact` v6 stopped including dotfiles;
the one upload here is a single `.exe`. All three moved to Node 24, which the
GitHub-hosted runners this project uses already have.

Verified by the workflows parsing and by `Checks` on `dev`, which is where a
bad pin is supposed to be found.

Files: `.github/dependabot.yml`, `.github/workflows/check.yml`,
`.github/workflows/site.yml`, `.github/workflows/update-components.yml`.

### 2026-08-31 — A transcript labelled with the model that was wished for

The owner's screenshot: a microphone recording made minutes earlier, marked
`Přesný`, when the fast model had done the work. Read off his own machine rather
than reasoned about — the archive's settings say `model: large-v3` with
`quality_choice` empty, which dates the value to before 20 August when the two
cards did not exist yet, and `AppData\Local\cz.znackarna.volocal\models` holds
only `ggml-large-v3-turbo-q5_0.bin`.

His own reading was right and is the interesting half: **an uninstall keeps the
archive on purpose**, so that recordings survive a reinstall — and the settings
ride along inside it. A wish written by an installation that is gone outlived
the model it named.

`resolve_transcription_model` then does what it is for: the wish cannot be
honoured, so the model that is on the disk answers instead, and the
transcription runs. What was wrong is one line after it — `set_model` was
handed `settings.model`, the wish, and the card reads that. Three places, two
truths: the settings held the wish, the cards on `Přesný`/`Rychlý` showed what
is actually installed (his own repair of 20 August), and the recording's label
showed the wish.

The choice now has a name, `model_to_record`, so that it can be tested without
running a transcription. That mattered: the first test went into `tools.rs` and
pinned the resolving, and putting the old line back left it passing. A test that
cannot fail for the fault it describes is worse than none, because it is
believed. The two tests now sit at the decision, and reverting it fails one.

The settings are left alone. The wish is the reader's, and one press on
`Rychlý` reconciles all three places.

### 2026-08-31 — A button that did nothing, and the reason nobody could tell

Reported alongside it: the microphone drew its peaks to his voice, pressing
record did nothing at all, and only a reinstall helped. There is no diagnosis
here, because there is no evidence — the log beside his archive does not exist,
and the installed 1.2.21 would not have written this kind of fault down anyway.

What could be established is why. `ErrorBoundary` catches a throw during render,
the loud kind where the screen goes. **React deliberately does not route a throw
inside an event handler to a boundary**; it goes to `window.onerror`, and this
application had no listener there and none for `unhandledrejection` either —
checked, not assumed. So a failing handler leaves the component running, the
state where it was, and a button that does nothing. Which is exactly what he
described.

`src/crashlog.ts` listens for both and sends them the same way the boundary
does. Nothing is prevented and `preventDefault` is called on neither, so the
console and `tauri dev` are unchanged; this only takes a copy on the way past.
And `recorder.start` now says why it refused — the stream and the phase — rather
than returning in silence, which was the other half of a dead button.

Its own test found a fault in it: `keepUncaughtErrors` stacked a listener per
call, which production never does and Vite's hot reload does on every edit. It
is idempotent now.

**This does not fix the microphone.** It means the next time it happens there is
something to read, and the answer to that report is *tell me before you
reinstall* — a live fault can be examined and a reinstalled one cannot.

172 frontend tests, 248 Rust tests, clippy and fmt clean.

Files: `src/crashlog.ts`, `src/crashlog.test.ts`, `src/main.tsx`,
`src/recorder.tsx`.
