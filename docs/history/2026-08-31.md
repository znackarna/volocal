### 2026-08-31 — Dependabot starts opening onto `dev`, and the three live bumps go in by hand

The reason its pull requests kept becoming ballast was one missing line.
`.github/dependabot.yml` named no `target-branch`, so it opened against the
default branch, which is `main` — the published branch, the one nobody commits
to. #214 sat there four days, and by the time it was read half of it was
bumping steps `dev` had already deleted.

`target-branch: dev` fixes that, and it has one cost worth writing down rather
than discovering: with it set, GitHub raises *security* updates only against
the default branch, so an advisory on an action will not arrive by itself. The
monthly run picks it up within the month. For four pinned actions that is the
trade worth making, and the alternative — pull requests nobody reads on a
branch nobody works on — was not protecting anything either.

**The three bumps that are still real were applied by hand**, so the pins are
current when `dev` next goes out: `checkout` 4.4.0 → 7.0.1, `setup-node`
4.4.0 → 7.0.0, `upload-artifact` 4.6.2 → 7.0.1. Every SHA was resolved from the
action's own tag before being written, not copied from the pull request.

The other three in #214 — `configure-pages`, `upload-pages-artifact` and
`deploy-pages` — are not applied and will not be: those steps left `site.yml`
when Pages was switched off on the 27th.

What was checked before applying them, because all three are major jumps:
`checkout` v7 refuses to check out a fork's pull request under
`pull_request_target` and `workflow_run`, and neither trigger is used here.
`setup-node` v5 began caching automatically when `package.json` carries a
`packageManager` field — it does not, and `cache: npm` is written out by hand
anyway, so nothing changes. `upload-artifact` v6 stopped including dotfiles;
the one upload here is a single `.exe`. All three moved to Node 24, which the
GitHub-hosted runners this project uses already have.

Verified by the workflows parsing and by `Checks` on `dev`, which is where a
bad pin is supposed to be found.

Files: `.github/dependabot.yml`, `.github/workflows/check.yml`,
`.github/workflows/site.yml`, `.github/workflows/update-components.yml`.

### 2026-08-31 — A button that did nothing, and the reason nobody could tell

Reported alongside it: the microphone drew its peaks to his voice, pressing
record did nothing at all, and only a reinstall helped. There is no diagnosis
here, because there is no evidence — the log beside his archive does not exist,
and the installed 1.2.21 would not have written this kind of fault down anyway.

What could be established is why. `ErrorBoundary` catches a throw during render,
the loud kind where the screen goes. **React deliberately does not route a throw
inside an event handler to a boundary**; it goes to `window.onerror`, and this
application had no listener there and none for `unhandledrejection` either —
checked, not assumed. So a failing handler leaves the component running, the
state where it was, and a button that does nothing. Which is exactly what he
described.

`src/crashlog.ts` listens for both and sends them the same way the boundary
does. Nothing is prevented and `preventDefault` is called on neither, so the
console and `tauri dev` are unchanged; this only takes a copy on the way past.
And `recorder.start` now says why it refused — the stream and the phase — rather
than returning in silence, which was the other half of a dead button.

Its own test found a fault in it: `keepUncaughtErrors` stacked a listener per
call, which production never does and Vite's hot reload does on every edit. It
is idempotent now.

**This does not fix the microphone.** It means the next time it happens there is
something to read, and the answer to that report is *tell me before you
reinstall* — a live fault can be examined and a reinstalled one cannot.

172 frontend tests, 248 Rust tests, clippy and fmt clean.

Files: `src/crashlog.ts`, `src/crashlog.test.ts`, `src/main.tsx`,
`src/recorder.tsx`.

### 2026-08-31 — The bubble that stayed at 100 %

The owner's screenshot: `Stahuji JavaScript pro online zdroje 100 %` still on
screen after the download had finished, waiting for him to press the cross.

**Two correct halves again.** `install_component` announces a component and
sends `download:progress` with a `complete` phase for the file that landed. What
ends a run is `download:complete`, and `install_bundle` was the only caller that
ever sent it. The first online import fetches yt-dlp and the JavaScript runtime
through `install_component` directly — a run of one that nobody closed.

`App.tsx` cannot simply clear on the `complete` phase, and the comment there
says why: in a bundle that phase arrives between files, so clearing on it would
flicker the bubble off and on. The gap is a run that never announced its end,
not a window that read it wrong.

`fetch_is_over` in `online_import.rs` sends the event at both places the import
fetches something, whether the fetch succeeded or not — the run this screen
started is over either way. The list is empty, which is truthful here, and
`SetupWizard` ignores a run it did not start (`startedRun`), so an empty list
cannot conclude somebody else's walk. Checked before writing it rather than
assumed.

**Not covered by a test, and it is worth saying why.** Observing an emitted
event needs a Tauri `AppHandle`, and no test in this repository stands one up;
the bubble's own behaviour lives in `App.tsx`, which is 1,960 lines with nothing
rendering it. Standing up either harness for one call is a bigger change than
the repair. Verified by construction and by reading every listener of the
event — which is weaker than the three repairs above it, and is recorded as
weaker rather than dressed up.

Files: `src-tauri/src/online_import.rs`.

### 2026-08-31 — The four latent faults, read against the screen: none of them is one

The owner said he wants things that would trouble a user not to happen, so
point C of the tidy-up plan was opened. It names four places where a selector
and the data it selects from are set independently, and calls them latent
faults of the same shape as the `Výkon` flash and the folder button. Each was
read against the screen it actually draws. **All four draw correctly today.**

**`previewTab` against `aiOutputs`/`summaryLength`.** The selector and the
data really can move apart — pick a summary length nothing was written for and
`summaryOutput` is `undefined`. But every one of those combinations already has
its own empty state, with the heading for that length, the sentence, and the
button that makes the missing document. The footer's Copy and Save follow
whether there is a text. There is no path to a blank panel.

**The note trio.** `addingNote`, `noteDraft` and `noteDraftTime` are set
together at every point where the draft's life changes — begun, cancelled,
saved. The two that are also set alone are the textarea's own `onChange` and
the pin button, which is what those controls are for.

**The AI trio.** `setAiRunning(true)` starts a one-second poll of the real
backend status that sets `aiRunning`, `aiProgress`, `aiDocument` and
`aiOutputs` from the same answer. A run and its result are tied together by
that loop; a wrong flag is corrected within a second, by construction.

**The two `check` copies.** `App.tsx` and `Settings.tsx` do each hold one, and
it is deliberate and documented in both: the archive refreshes its copy going
into Settings and again coming out, Settings reads its own on mount, and
`checkedCompute` beside it exists because a question and its answer were once
allowed to disagree. Unifying them is a tidy-up, not a repair.

**So nothing was changed in any of them, and that is the finding.** The plan
called them latent, which was right, and the honest reading of "latent" here is
that the code is correct and only the shape is risky. Rearranging four working
mechanisms to make a shape look safer is how a working screen acquires a fault.

**What was missing was the test, and that is what went in.** `Detail.tsx` is
the largest screen in the application and nothing rendered it — every fault of
this shape that has ever reached the owner was found by his eye. So
`src/detail/screen.test.tsx` mounts the whole screen against a mocked backend
and pins five things: that it renders at all; that a summary length with
nothing behind it offers to make one instead of showing a blank; that choosing
the length that does have a summary brings it back; that a finished run stops
the screen saying it is running; and that a note begun and abandoned leaves no
draft behind the next time the editor opens.

Getting it to mount is itself worth recording, because the next person will hit
the same three: the screen needs `PlayerProvider` and `RecorderProvider` around
it, jsdom has no `ResizeObserver` and no `scrollIntoView`, and the transcript is
drawn word by word so no element holds a whole sentence — it is read off the
container's text.

Proved by breaking it: with the summary empty state disabled, two of the five
fail. Restored, all five pass. 184 tests, 22 files.

Files: `src/detail/screen.test.tsx`.

### 2026-08-31 — Stop wears a square, and a button that only looked crooked

The owner: the button that starts a take has the red record dot, so the one that
ends it should have the stop mark. It does now — the same 10 px in the same
place, `currentColor` rather than red, because red is destructive here (Smazat,
Odebrat) and stopping a take destroys nothing. 2 px of radius, enough to lose
the hard corner at that size without reading as a circle.

**And a photograph of `Nová složka`, which turned out to be almost nothing.**
The text looked low against the plus. Measured against the real stylesheet in a
browser rather than argued about: flexbox centres both children exactly, the
plus sits on zero, and what is off is the ink of the letters.

The first number reported to him was wrong — 0.67 px, from a harness whose text
range included the whitespace JSX leaves in the node. Measured faithfully it is
**0.17 px**, a quarter of a device pixel even at his 150 %.

The measurement worth keeping is the other one. The same class carries four
labels, and the offset is set by which letters are in them: `Rozpoznat znovu`
sits **2.17 px** low because of the descender in `p`, where `Nová složka` has
none. No `line-height` centres both — 17 px and 17.5 px were measured and only
move the whole set. Optical centring is per-string and CSS cannot do it.

So nothing was changed. Correcting the button he photographed would have thrown
the three speaker buttons ten times further out, and the only honest way to fix
that one alone is to stop sharing the class — a lot of machinery for a quarter
of a pixel.
