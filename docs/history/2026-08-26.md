### 2026-08-26 — A release now redeploys the page by itself

1.2.21 went out at 07:48 and the published page went on offering 1.2.20 for the
rest of the morning. Nothing was broken and nobody had forgotten anything: the
number on GitHub Pages is read from the latest release at deploy time, and
`site.yml` deployed on a push touching `docs/site/**` — which a release is not.
The page was current with a release that no longer existed.

**It now also deploys on `release: published`.** That closes the loop the
workflow already had one half of: the version was automatic, the moment to
apply it was not.

**And `version.ps1` now moves the page's own two numbers** — the hero and the
closing — with the seven other places a version is written down. What Pages
serves has them rewritten anyway; the file's copy is what a reader sees when
the page is opened from disk or handed over as a bundle, which is exactly where
a stale number is least expected. Both were on 1.2.20 and are on 1.2.21.

What is still by hand is the review copy on `claude.ai`, and it stays that way:
publishing there is an account action, not something a workflow can hold a key
to. It is the page under discussion, not the page being read.

Verified by watching the deploy and reading the number back off the live page.

Files: `.github/workflows/site.yml`, `scripts/version.ps1`, `docs/site/index.html`.
