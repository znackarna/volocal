# 2026-08-20

### 2026-08-20 — Online import stopped after a megabyte, and the megabyte is the diagnosis

The owner pasted a YouTube link into *Online služba* and got back, inside the
Czech dialog, a line of yt-dlp's English:

```
ERROR: unable to download video data: HTTP Error 403: Forbidden
```

Two separate things were true at once, and separating them is most of the work.

#### The link in the screenshot no longer exists

`qkEl5hPXCXM` returns 404 from YouTube's own oembed endpoint, and every player
client answers *Video unavailable*. So the exact reproduction from the picture
cannot be run again — the video was taken down between the attempt and the
diagnosis.

That is not the fault, though, and believing it was would have closed the
report. The message in the picture is a **403 on the media data**, which can
only be reached *after* extraction succeeded — when the owner tried it, the
video was there and yt-dlp had already read its formats. Something else refused
the audio.

#### Every video failed, at the same place

`dQw4w9WgXcQ` — public, four minutes, certainly present — with the arguments
`online_import.rs` actually passes:

```
[info] dQw4w9WgXcQ: Downloading 1 format(s): 251
ERROR: unable to download video data: HTTP Error 403: Forbidden
```

So the feature was broken for everything, not for one link.

What located it was asking *how much* arrives before the refusal rather than
*whether* anything does. With `--http-chunk-size 10K` the bar climbs to 28.4 %
and stops; with `100K`, to 26.2 %. Both leave about **950 KB** on disk out of
3.27 MB. A ten-kilobyte ranged request — yt-dlp's `--test` — succeeds outright.

An address that serves a megabyte and then refuses is not an expired address, a
blocked address or a rate limit. It is YouTube's **PO token** condition: the
media URL its current default players hand out is good for a preview and needs
a token this application has no way to mint before it will serve the rest. The
first megabyte is the tell, and it is why the failure reads as a network error
when it is an authorisation one.

#### The embedded player's address carries no such condition

Downloading the same format through each client, in full rather than as a
sample, gives one answer:

| client | result |
|---|---|
| `web_embedded` | **3.27 MB, complete** |
| `android_vr` (a default) | 403 after ~1 MB |
| `web`, `mweb`, `android`, `tv_simply` | no audio-only format offered at all |
| `tv` | *The page needs to be reloaded* |
| `ios` | no audio-only format offered |

So `online_import.rs` now passes:

```
--extractor-args youtube:player_client=web_embedded,default
```

Order is the whole of it. `default,web_embedded` still fails — yt-dlp keeps the
first client's address for a duplicate format id, and with the defaults first
the 403-prone address wins the tie. Named first, the embedded player's address
is the one that gets downloaded; `default` stays behind it as the fallback for
what that player will not open.

The argument is addressed to `youtube:` and reaches no other extractor, which
matters here more than usual: what this application supports is what yt-dlp
supports, 1752 sites as counted on 16 August, and a YouTube repair must not be
a change to any of the other 1751.

#### Verified

Full audio through the application's own pipeline — `bestaudio/best`,
`--extract-audio --audio-format m4a --audio-quality 0` — on three videos:
`jNQXAC9IVRw` (0:19, 515 KB), `9bZkp7q19f0` (4:13, 12.2 MB), `kJQP7kiw5Fk`
(4:42, 14.2 MB). All three complete; before the change all three stopped at a
megabyte. `cargo fmt`, `cargo clippy --all-targets -D warnings` and the 215
tests are clean.

#### What was not done, and why

**yt-dlp was not updated.** The natural first guess for a YouTube breakage is a
stale binary, and `components.json` pins `2026.07.04` — which is, today, the
newest stable release there is. Nothing to move to.

**No PO token provider was added.** Minting one means a second runtime service
beside yt-dlp and deno, for a feature that now works without it. If the
embedded player is closed off later, that is the decision to reopen, and this
entry is the argument for it — not a reason to build it in advance.

**The dialog still shows yt-dlp's English inside Czech copy.** That is how the
owner could report this at all: the tail of stderr is what identified a 403
rather than a dead link. A translated summary would have said *stahování se
nezdařilo* and told nobody anything. Worth revisiting as its own piece of work,
with the raw text kept somewhere reachable.

### 2026-08-20 — The setup fails on somebody else's network, and the application had thrown away the reason

Second report of the day, from a machine that is not here: at home the
components download, at a friend's house the first run ends on *Instalace se
nezdařila* with two red lines, both saying **Nepodařilo se spojit se serverem**
and then a huggingface.co URL over four lines.

That message names the one thing the reader cannot act on. Which server it was
is in the sentence; **why it did not answer is not**, and the difference between
a name that does not resolve, a proxy nobody configured, an antivirus opening
the connection, a firewall, and a cable that is out is the whole of the repair.

The reason was not missing. It was collected and discarded. `download_file`
already put the failure into `UserMessage::detail`, and `detail` is by design
only shown when the dictionary has *no* entry for the code — and
`download.connection_failed` has one. So the better the message got, the less
it said.

#### What is on screen now

```
Nepodařilo se spojit se serverem huggingface.co: client error (Connect):
dns error: No such host is known. (os error 11001)
```

The host instead of the whole address — a repository path, a forty-character
commit and a file name are four lines of small red type that answer nothing —
and then the innermost cause. `connection_cause` drops reqwest's outermost
layer, which reads *error sending request for url (…)* and only repeats what
the sentence already said, and joins what is under it.

`download.rejected` gained the status code for the same reason: *Server odmítl
soubor vydat* is equally true of 403, 404 and 451, and they are three different
problems.

**This is English inside Czech copy, and it is the second time today the raw
technical text is what made a report actionable** — the yt-dlp 403 above was
identified from exactly such a line. `Copy is for people` still holds for
everything a person can act on; a transport failure on a machine nobody here
can touch is not that.

#### The instrument, because the fault is not reproducible here

Everything works on this network, so there is nothing to debug — which is the
case the test-card rule was written for. `scripts/network-check.ps1` runs on the
machine that cannot download and separates the steps the application performs
in one breath:

- what the interfaces and their DNS servers are;
- whether a proxy is configured in Windows, in the environment, or by autoconfig
  — the classic works-in-the-browser-fails-in-the-application difference, since
  a proxy set in Windows is not a proxy set in the environment;
- which antivirus is installed, so that the certificate issuer below is
  recognisable when it turns out not to be Amazon's;
- per host — `huggingface.co`, `us.aws.cdn.hf.co`, `cdn-lfs.hf.co`, and the two
  GitHub hosts the programs come from — the name lookup, then **every address it
  resolves to** separately, then the secure handshake and **who issued the
  certificate**;
- and last the real thing: the first 64 KB of the speech-detection file,
  through the redirect, which is the only step that can fail with everything
  above passing.

Two details worth keeping. It is written in **pure ASCII with CRLF**: Windows
PowerShell 5.1 reads a `.ps1` as ANSI unless it carries a BOM, and one em dash
in a comment made the whole file a parse error on the first run. And an address
family is chosen per address rather than left to the client — a machine with no
IPv6 route otherwise answers eight AAAA records with eight lines of *Rodině
adres soketu neodpovídá žádná z nalezených adres*, which reads as eight faults
in a host that is perfectly fine. Those are reported as skipped now, and the
handshake is made through an address that actually answered.

A report where half the lines say FAIL on a healthy machine cannot be read, and
this one is going to be read by somebody standing in a friend's living room.

#### Not decided yet, deliberately

No mirror, no fallback host, no retry policy. Each of them is a guess at a cause
that has not been measured: a mirror repairs a blocked name and does nothing for
a proxy or an intercepted handshake. The measurement comes first — that is the
whole point of the script — and 1.2.16 ships the two things that are right
regardless of the answer: the working online import, and a failure that says
what it was.

### 2026-08-20 — Correction: the 1.2.16 commit carries the presentation site as well

`ffdab3a`, whose message is entirely about the online import and a download that
says why, also contains the whole of `docs/site/` and the records of 18 and 19
August — about ten thousand lines that have nothing to do with the release it
names.

Nothing was lost and the tree is right. What is wrong is the record, which is
the thing this folder exists to keep.

How it happened is worth writing down, because the shape recurs. The
presentation site had been committed **locally and never pushed**, so `main`
here was one commit ahead of `main` there. A branch taken from the local `main`
therefore carried that commit too, and GitHub computes a pull request's diff
against *its* `main` — so the review, the checks and the squash all took in work
nobody had put up for review. The commit that came back is honest about what it
was written for and silent about half of what it contains.

**The lesson is one command**: `git log --oneline origin/main..main` before
branching. A local commit that has never been pushed is invisible in every view
that matters — `git status` is clean, the diff against `HEAD` is empty, the
branch looks like it was taken from what is on the server. Only that comparison
shows it.

Not rewritten, deliberately. `main` is public and the release is built from it;
a force-push to correct a message would cost more than the message is worth, and
this repository's rule for a superseded record is to write the correction after
it rather than to edit the past quietly. So: **`ffdab3a` is two pieces of work,
and this is the second one's name.**

### 2026-08-20 — Delete a model by hand and the application knows, but will not say

Two reports, an hour apart, with one cause under them.

> Když ručně smažu model a nezůstane žádný, píše mi upozornění že mám doplnit,
> ale v seznamu modelů a nástrojů chybí označení toho, co mám vlastně stáhnout.

> Ve výběru modelu se zruší model, protože není stažený a pak vzniká chaos při
> opětovném stažení.

**The application decides what is needed from static flags and from the
drivers, and never from what is on the disk.** Everything below follows from
that one sentence.

#### The card asks the disk; the list reads a flag

`Chybí 1 položka nutná pro přepis` comes from `tools::check`, which looks for
`ggml-{settings.model}.bin` and does not find it. The badge on the listing that
`Doplnit` opens is `item.required && !item.complete`, and `required` is the
catalogue's own flag — **true of `ffmpeg` and `vad` and of nothing else.**

It is not a bug in the flag. No single transcription model is required and no
single whisper build is: any one of several will do, and a per-row boolean has
no way to say *one of these*. So the two never disagree until a set requirement
goes unmet by a row that is not individually required — which is exactly what
deleting the model does.

The result is a screen that says something is missing and then refuses to say
what, in a list of fifteen rows.

`ToolCheck` now carries `needed`, filled from the same reads that filled
`issues`: ffmpeg for either half of the pair, the whisper build the drivers
call for, `vad`, and — for the model — **the component that writes the file the
setting names**, so somebody who deleted `ggml-large-v3.bin` is offered the
model they had rather than the one this machine would have been sold. That
lookup is read off the catalogue's own `verification_path` rather than written
down a second time; a table mapping model names to component ids would be one
more place to forget when a model is added.

#### The card that ignored the model already on the disk

`const quality = chosen ?? recommendedQuality(usesGpu)` — the drivers, and
nothing else. On a machine with a graphics card the dialog therefore reopened
on **Přesný, 3,0 GB ke stažení**, with **Rychlý** beside it wearing the word
**staženo**.

The recommendation is not wrong; it is an answer to a different question. *Which
model suits this machine* is what a first run asks. *What happened to mine* is
what this reader is asking, and the disk is the only thing that answers it. The
recommended quality is still tried first, so a machine holding both is given
what it would have been given anyway.

#### And then the chaos, which was not where it looked

Choosing the model that is already there leaves nothing to fetch, and the
guided run has a branch for that: the button becomes `Zavřít` and calls
`dokonci([])`. `dokonci` writes `quality_choice` and, in that branch,
deliberately **not** `settings.model` — the model is `App.tsx`'s to write from
the pending record, once `download:complete` says the file landed.

No download, no event, nothing written. So the dialog closed, `settings.model`
went on naming the file that had been deleted, and the banner asking for it
stayed up. Pressing again did the same thing again.

**The first attempt at this fixed a line that never runs.** It went into
`start()`, on the reasoning that `install_bundle` returns `Nothing` for a list
of things it already has and therefore emits no `download:complete` — all true,
and all beside the point, because with nothing selected the button is not the
one that calls `start()`. The reasoning was sound about a mechanism and wrong
about the screen, and what caught it was writing the test: it drove the actual
button and the setting still was not written.

The condition `App.tsx` guards is that the file exists. In `dokonci` it
demonstrably does — `complete` is the catalogue's own answer about the disk —
so the model is written there, and the record that exists for a choice
outliving the screen is left for the case it was built for.

#### And the row it marked was the wrong one, from his own machine

> Označil jako nezbytný přesný model. Přitom jsem smazal rychlý.

Read off the database rather than guessed at, which took one query:

```
model          = ""
quality_choice = "fast"
```

**`settings.model` is empty**, because it is written when a download finishes
and this machine's never had. So `component_for_model("")` matches nothing, and
the answer fell straight through to the drivers — a graphics card, therefore
`model-large`, therefore *Přesný* and three gigabytes marked as necessary at a
reader who had chosen *Rychlý*, could see they had chosen it, and had just
deleted 575 MB.

The right model for the computer and the wrong answer to the person. And the
answer to the person was sitting in the row underneath: `quality_choice`
records what was chosen and survives the model being empty, which is precisely
the state this whole day has been about.

Three answers now, in the order of how much each knows about this reader: the
model the setting names, then the choice that was recorded, then the drivers —
last, being a guess about the computer made where there is nothing else to go
on. The test asserts both choices in one case on purpose: the machine's own
fallback agrees with one of them, and which one depends on whether the computer
running the test has a graphics card, so together they always tell the answer
apart from the guess.

**Two of today's four faults were mine, found within an hour of writing them.**
That is not a reason to slow down; it is the argument for the report loop being
this short, and for reading the reporter's own state instead of reasoning about
what it must be. One query beat three plausible theories about what `model`
contained.

#### Three gigabytes on one click, and the smaller card was the one that asked

> Když jsem klikl na první model, začal se automaticky stahovat, místo aby se
> mě zeptal dialog na souhlas.

`chooseModel` in Settings called `api.download` straight from the press.
`chooseEditor`, one section down the same screen, has asked since it was
written — *Asked first when it costs gigabytes* — with a dialog naming the
size.

So the same gesture, a hundred lines apart, behaved two ways, and **the one
that asked was the smaller of the two in the case that matters**: the language
editor is offered where somebody has gone looking for it, while the
transcription model is the card people actually press.

The difference had been carried in words the whole time.
`settings.transcription.modelNote` read *Výběr nestaženého modelu zahájí
stahování* — a true sentence, and a warning standing in for a control. It is
not a way back, and there was none except finding the running download in the
progress bubble and stopping it.

Both cards share one dialog now — the state is `downloadConfirm` rather than
`editorConfirm`, because it no longer belongs to one of them — and the note
says what the screen now does instead of warning about what it used to.

Asked before it was written, because the answer changes the work: the request
was read at first as *ask before any row in the by-hand list downloads*, which
is a different and much larger change. It is not what was meant — *ten dotaz na
stažení jsem myslel jen u přepínače modelu v nastavení* — and the by-hand list
keeps starting on a press, which is what that list is.

#### It is tested, which was the second question

The first version of this entry said none of the three was covered and named
the screenshot check as what would catch them. That was true of what had been
written and false about what was possible: the wiring is reachable from
`@testing-library/react`, which this repository already has and already uses.

Four Rust tests and four in the window:

- `check` on an empty folder raises complaints **and** leaves something to
  press for each — asserted as the pairing, `issues.is_empty() ==
  needed.is_empty()`, rather than as a list. Nothing asserts on ffmpeg or on
  the whisper build, and that is not laziness: `find_program_in` falls back to
  `PATH`, so on a machine with ffmpeg installed for other reasons neither is
  missing. That is a real property of the check and a test asserting otherwise
  would only pass here.
- the model to offer is the one the setting names; a model no component
  delivers still leaves one of the offered pair to press; a model put back
  stops being asked for.
- the listing renders and **one** row wears the badge, the model's, though the
  catalogue calls it optional — and none does on a complete installation.
- the cards open on the model that is on the disk though the drivers recommend
  the other, and closing on it writes `model` and `quality_choice` to the
  settings without any download having happened.

All four were run against the code as it was before the repair, and three of
them fail there. A test that passes both ways is not a test, and the fourth is
the one deliberately asserting that nothing is marked when nothing is missing.

Rows are found by the name the dictionary gives them, read out of the
dictionary rather than typed into the test, so rewording a catalogue entry
cannot break it.

#### Verified

`cargo test` 222, `clippy --all-targets -D warnings`, `cargo fmt`,
`npm run build`, `tsc --noEmit`, 137 frontend tests — eight of those twelve
numbers are new today and eight of them are these faults.

What is still not covered is what a rendered tree cannot see: that the badge is
legible, that the card reads as chosen. The screenshot check remains the answer
to that and remains deferred — but it is no longer the answer to *this*, which
is what the first version of this entry got wrong.

### 2026-08-20 — One truth, and it is the disk

A review of the whole download-and-dependency flow was asked for in these
words: *prostě ať to dává smysl, a člověk s omylem se neocitne v chaosu*. It
came back with eight findings, and under them one sentence worth more than the
list:

**The application kept three separate notes saying *this is the one I asked
for*, and not one of them asked whether the file had arrived.**

| note | where | how long it lived |
|---|---|---|
| `pending-model` | `localStorage`, honoured by `App.tsx` | past a restart; nothing cleared it |
| `MODEL_WANTED` | `localStorage`, read by Settings | until the file appeared, however long that took |
| `startedHere` | a `Set` inside the wizard | until the component was deleted |

Three lifetimes, three consumers, and each of the day's earlier repairs had
fixed one consumer. Every paradox the review found is one of those notes
outliving what it described:

- pressing a model row and closing the list mid-download wrote the setting for a
  file still coming down; stopping one row and letting *any* other row finish
  wrote it for the partial;
- a first run rescued by `Zkusit znovu` never wrote the model at all, and
  concluded *Vše je připraveno* with the banner still up behind it;
- a record left by a run interrupted at the window closing survived the restart
  and would fire on the next unrelated download — the reporter's own machine,
  `model` empty and both models on disk as `.cast` partials, was one interrupted
  run away from it;
- a cancelled download left a card reading *stahuje se…* for ever, and an intent
  that could fire months later over a choice made since.

#### The rule

**A note may say what somebody wanted. Whether it arrived is a question for the
disk, and there is now one place that asks it.**

`resolve_transcription_model` in `tools.rs` searches, in order: what the setting
names, what `quality_choice` implies, then any offered model that is actually
here. It is the same shape as `resolve_editor_model` directly below it, and for
the reason written there — *asking for another multi-gigabyte download would
create a loop*. The transcription model had no such repair, which is why a
deleted file could stop the application dead with a perfectly good model sitting
beside it.

`ToolCheck` reports `model_whisper_id`, which model actually answered, and the
card in Settings draws that rather than `settings.model`. The two part company
exactly when the setting cannot be honoured, and highlighting the record there
would be the same paradox in a new place: a card marked as chosen naming a model
that is not the one working.

With that in hand, **`pending-model` is deleted rather than fixed.** There is no
note to keep in step, so there is no note to go stale: choosing a quality
records the choice, and the model that arrives is found because it is there. The
other two lost their authority rather than their existence — `startedHere` and
`MODEL_WANTED` still say what was wanted, and neither can write a setting any
more without the catalogue's `complete` agreeing.

#### Two more, and one of them was a test lying

`dropped` holds what was taken out of the queue before a worker reached it, and
it is appended to what `download:complete` reports as unfinished. Re-queueing
never took the component back out, so **stop, reconsider, press again** ended
with the file on the disk, a tick on its row, and the run announcing it as
failed.

No test could have caught it, and this is the part worth keeping: `admit` in the
test module was **its own copy of the accept loop**, not the real one. A copy is
not a model — it passed while the real loop did something else, and it had no
`dropped` in it at all. The loop is `accept_into_queue` now, called by both, and
the test drives the actual decision.

And the sentence saying what is missing named `ggml-.bin` on a machine where
`settings.model` is empty — a file name with nothing in it, shown to the reader
least able to guess what it meant. It and the row offered to fix it now come
from one function, so they cannot name two different things.

#### Considered and left alone

The review's own dismissals stand and are worth recording: the complete `.cast`
answered with 416, a stale `.cast` from a moved URL, a server answering 200 to a
range request, a connection dropping mid-file — all handled, each with the
comment that explains it. Changing the models folder mid-download lands the file
in the old one, which is deliberate and documented. A by-hand row still starts on
a press: that was confirmed with the owner today and is what that list is.

Left as it is: fetching both models by hand and then closing settles on the fast
one, because `MODELS` is declared fast-first. An accident of declaration rather
than a decision, written down here so that whoever minds can find it.

#### Verified

`cargo test` 227, `clippy --all-targets -D warnings`, `cargo fmt`,
`npm run build`, `tsc --noEmit`, 137 frontend tests, `i18n:check`, `docs-check`.
Four new Rust tests: the offered model names held to the catalogue that
downloads them, a setting that cannot be honoured giving way, a setting that can
be honoured being honoured anyway, and stop-reconsider-press-again.

### 2026-08-20 — Five of the six weak spots, from the full-application audit

Fable was asked to go through the whole application and write a repair plan for
somebody else to execute. Six items came back, ranked by harm × likelihood.
This entry is five of them; the sixth — a microphone take that exists only in
memory until it is saved — is its own piece of work and its own entry.

Every one of them was verified against the code before it was touched, and each
has a test that fails on the version before the repair.

#### The update installer walked over a running take

`downloadAndInstall` ends in `process::exit(0)`, and `exit` raises no
`tauri://close-requested` — so the recorder's close guard, written on 17 August
for exactly this loss, never heard it. **The gesture that was made safe was the
window's close button; this is the same loss through a different door.**

`install()` now refuses while the phase is `recording` or `preview`, which are
the two the close dialog guards, and says why. A refusal rather than a question:
the way out of both is one press — save it, or throw it away on purpose — and an
update that can wait is not worth an *install anyway* button beside an
unrepeatable recording. `ready` (an open microphone with nothing recorded) and
`saving` go ahead, the same two exceptions the close guard makes.

#### The dictionary corrected the text and not the words

**The screen, the subtitles and click-to-seek are drawn from the word timings,
not from `text`** — `Detail.tsx` says so in a comment, and `export.rs` cuts
captions from `words`. `apply_dictionary` ran the rules over `text`, where a
multi-word entry matches, and then **over each word chunk separately**, where a
pattern containing a space can never match anything.

So `součas DNA → součást DNA` — the dictionary's own worked example — corrected
the stored text, left the screen and the SRT saying `součas`, and made
plain-text export disagree with the captions beside it. The reader was told N
segments had changed and could see nothing change.

The rules now run over the chunks joined with a single space (`whisper.rs`
stores each `trim_start`ed, so that join is a faithful reading), and every match
is written into the chunk it opened in. Chunks the match swallowed are dropped,
and their timestamps go with them; the surviving chunk keeps its own time, which
is the phrase's start. **No timestamp is computed, moved or scaled** — the
critical invariant is untouched.

**The existing test passed the whole time**, because it hand-built `"pět set"`
as a single chunk. Real tokenization never produces that: `whisper.rs` opens a
new chunk at every token that starts with a space. A fixture that cannot occur
is a test of nothing.

#### A panicking language-edit worker locked the feature until restart

The line freeing the busy slot was the last line of the worker closure, and a
panic does not pass through there. From then on every *Vylepšit* answered *už
běží jinde*, the card stood at whatever percentage it had reached, and the
module listing kept llama.cpp and seven gigabytes of model locked — with nothing
saying why.

This is the defect `WaveformJob` was given a drop guard for on 17 August, found
in a second place nobody had looked at. `Slot` holds the claim for the length of
a run and gives it back however the run ends, clearing only its own id so a
thread finishing late cannot unlock the run that replaced it; `caught` wraps the
work the way `without_panicking` wraps the transcription pipeline, so a panic
reaches the reader as an error and the log as text.

#### A re-transcription left the previous run's speakers behind

Speakers were inserted with `ON CONFLICT DO NOTHING` **outside** the transaction
that rewrites the segments, and nothing ever deleted the ones a new run did not
produce. Transcribe a diarized interview again with fewer voices found, or with
diarization off, and the recording kept named people with nothing in the
transcript they had said. A failed save left the new speaker rows behind after
the segments rolled back.

Both writes are inside the transaction now, and `keep_only_speakers` removes
what this transcript has no use for while leaving the rest untouched — which is
what lets a name somebody typed survive a second run. **What cannot be promised
is that a kept name still belongs to the same voice:** clustering may hand
`speaker_1` to somebody else between two runs, and no code here can tell.
Recorded rather than quietly traded away.

#### A damaged row made a recording vanish

`list_recordings` used `filter_map(|r| r.ok())`. A row the mapper cannot read
was dropped in silence, and the archive then showed the recording as simply not
being there — which a reader can only take as *somebody deleted it*. This is the
one screen the owner trusts to say what exists.

Failing the whole read is not the answer either; one bad row must not blank the
archive, which is what 1.0.4 was. The ids are read a second time, forgivingly —
`id` alone, the primary key, which cannot be the column that failed — and
anything that did not map comes back as a card in the error state naming itself.

The test damages a row the way a real archive can: `NOT NULL` rules out a
missing value but not a wrong *type*, and a column with TEXT affinity keeps a
BLOB as a BLOB. That is a torn write or a half-restored file.

#### Verified

`cargo test` 237, `clippy --all-targets -D warnings`, `cargo fmt`,
`npm run build`, `tsc --noEmit`, 142 frontend tests, `i18n:check`, `docs-check`.
The update guard and the two rendered tests around it were run against the code
before the repair and fail there.

### 2026-08-20 — The take is on the disk while it is still being made

The first item of the audit, and the one the ranking put above everything else:
**a microphone take existed only as a `Blob` in webview memory until somebody
pressed save.** `MediaRecorder` was started with no timeslice, so the chunks sat
in a JavaScript array and nothing was written anywhere.

The close guard of 17 August covers the deliberate gesture and covers nothing
else. A renderer crash, a graphics driver reset — plausible while whisper is
working the same card, because recording during a transcription is allowed — a
power cut, or a restart from Windows took a two-hour interview and left nothing
behind.

It is the one artefact in this application that cannot be made again. A
transcript can be produced from its recording, a document from its transcript, a
component from its download. A take can be produced from nothing.

#### What happens now

`recorder.start(3000)`. Every slice goes to the array as before **and** to a
shadow file beside the recordings, `.take-in-progress.webm`, through
`append_take_chunk`. The slices of one `MediaRecorder` concatenate into a
playable WebM — the first carries the header, the rest are clusters — so what a
crash leaves is a file that can be listened to, not a fragment.

Three decisions inside that, each with a reason:

**One promise chain, not a call per slice.** Two appends in flight can land the
other way round, and out of order those clusters are not a file. Every slice is
queued behind the last.

**No failure reaches the screen.** This is a net under a recording in progress,
and a dialog about the net would interrupt the very thing it exists to protect.
The take in memory is unaffected by a failed append either way. It goes to
`volocal-log.txt`.

**One file name, not one per session.** There is a single recorder and it can
only be making one take at a time. A new take truncates what the last one left,
and the prefix is deliberately not `.download-`, which `clear_leftover_imports`
deletes on sight at every start.

#### The rescue, and what keeps it honest

At the next start, anything left in the shadow above 4 KB — the same floor
`save_microphone_recording` refuses below — is renamed to
`Záznam <stamp> (obnovený).webm` and gets an archive row.

**That is only sound because every deliberate ending deletes the shadow.** Save
deletes it, in Rust, once the audio is in the archive under its own name —
there rather than in the window, so a save the window never hears the end of
still cleans up after itself. `Zahodit` deletes it. Closing the microphone
deletes it, which is the path the close dialog's *zahodit* takes. So anything
still there is a crash by definition, and handing it back cannot resurrect a
recording somebody chose to be rid of. The test for that half is as important as
the test for the rescue, and both are written.

WebM rather than the M4A a saved take gets: converting needs ffmpeg and a
startup is not the place to shell out. The archive already accepts a `.webm`
here — the failed-conversion path leaves one under the same kind of name.

**A correction to this entry, made an hour after it was written.** It said no
duration was claimed because reading one needs ffprobe, and that the archive
would fill it in when the recording was opened. **The second half was not
true.** `probe_duration` runs where a recording is *created* — an import, the
watched folder, a saved take — and nothing updates a duration afterwards, so a
rescued row would have read 0:00 for ever. It is asked for at the rescue now:
one ffprobe over one file, on a start that follows a crash, which is not
something every start pays for. Where there is no ffprobe the answer is 0.0 and
the row says nothing rather than something wrong — which was the only sound half
of the original claim.

**And that repair was itself wrong, which the owner found by running it.** He
recorded twelve seconds, ended the application in Task Manager, and the rescued
card said **0:00**. `audio_duration` asks ffprobe for `format=duration`, and a
file `MediaRecorder` produced has no duration in its header — it is streamed out
as it goes and nothing ever returns to fill the header in. ffprobe answers
`N/A`, the parse fails, and the answer is 0.0.

The timestamps are still there, so the last packet's is the length.
`audio_duration` falls back to reading them when the header says nothing: 56 ms
over that twelve-second take, because it reads packet headers rather than audio.
The header is still asked first, being cheaper and being what every other tool
would answer.

The test that now covers it had to be fixed before it was worth anything: its
fixture was an ordinary ffmpeg-written WebM, which *does* carry a duration, so
it passed against a file no crash could produce. It is written with
`-f webm -live 1` now — the way a browser writes — and it asserts the header
cannot answer before it asserts that the card can.

**Twice in one afternoon, on the same field, in the same way: written as a fact
and not checked.** The first time a `grep` would have shown it. The second time
nothing but running the thing would have — which is what the owner did, and it
is the argument for having the application open while the work is being done
rather than after.

#### Verified, and what is not

`cargo test` 241 — four new ones over the rescue: a take of real size comes back
as a recording pointing at bytes that exist, a discarded one does not, a
too-short one is swept rather than listed, and an ordinary start finds nothing.
`clippy --all-targets -D warnings`, `cargo fmt`, `npm run build`, `tsc`, 142
frontend tests, `i18n:check`, `docs-check`.

**And the part the test suite cannot reach was measured rather than assumed.**
There is no `MediaRecorder` in vitest, so the slicing itself was driven through
a real Chromium — which is what WebView2 is — against this machine's own ffmpeg,
with the exact arguments `save_microphone_recording` passes.

A 440 Hz tone, three seconds, `recorder.start(1000)`: four slices of 11 778,
12 358, 12 358 and 8 727 bytes. Joined, they are a `matroska,webm` that ffmpeg
converts to AAC 48 kHz stereo, 3.72 s, and a Goertzel over the result puts
1 286 923 of energy at 440 Hz against **0.0** at 1 000 Hz. The tone that went in
is the tone that comes out.

**Then the case that actually matters.** After a crash the last slice never
arrives — it is produced by `stop()`, which nothing calls. So the file was
truncated to the first three slices, 36 494 bytes of 45 221, and converted
again: ffmpeg says *File ended prematurely at pos. 36494*, **exits 0**, and
writes 3.00 s carrying the same 1 286 923 at 440 Hz.

That is the whole claim, demonstrated: what a crash leaves is a file, not a
fragment. The loss is the slice in flight — at most the three seconds of the
timeslice, and here exactly the 0.72 s the final slice held.

Still untested by machine: the crash itself, which is what the rescue function
exists for, and the rescue function is what got the tests.


### 2026-08-20 — *Stahuje se…* about nothing, found by looking at the screen

> Ukazuje i že se stahuje, ale nestahuje.

The transcription card said **stahuje se…** under *Přesný* with nothing coming
down, on a machine where that had been true at some point weeks ago.

It is the day's own disease once more, and this time in the copy: **the card was
drawing an intent and calling it a fact.** `MODEL_WANTED` records which model was
picked before it was on the disk, and the label was `card.id === modelWanted` —
so the word survived every ending the intent survived, which was all of them
until this morning.

The repair earlier today cleared the intent when its download visibly failed or
was stopped. That closed the case going forward and did nothing for the one
already stored: an intent left by a download that ended while the application
was closed is never told anything, and it sat in `localStorage` saying
*stahuje se…* for ever.

Two changes, and the first is the rule:

**The label follows the live download and nothing else.** `App.tsx` passes which
component is actually coming down, and a card says the word only about itself.
An intent with no download behind it now shows the size, which is true: the
model is not here.

**And a stale intent is dropped on the way in.** On the first read of the screen
an intent is either wanted-and-arrived, or coming down now, or nothing —
because every later read happens *during* a download. That is where one made
weeks ago is recognisable, and it is the only place. Read through a ref rather
than a dependency, so that `load` is not rebuilt every time a download starts
and the whole screen reloaded with it.

The intent itself stays. It has a real job — remembering what to write when the
file lands — and it does that job well. What it may not do is speak for the
present tense.

### 2026-08-20 — The menu measured the window and the dialog was what cut it

Reported from the running application: pressing **Uložit** in the
improved-transcript dialog dropped a menu whose bottom half was gone. TXT was
readable, MD was half a line.

`DocumentSaveMenu` already knew a menu can run out of room — it has an
`opens-above` variant and a measurement to decide. **The measurement asked the
wrong box:**

```
const roomBelow = window.innerHeight - bounds.bottom;
```

That dialog is 760 px tall inside a much taller window, so below the footer
there were hundreds of window pixels and twenty-six dialog ones. The window
said *plenty of room*, the menu opened downwards, and `.dialog` — which carries
`overflow-y: auto`, and therefore clips — took the rest.

It measures the first ancestor that clips now, and the window only where no
ancestor does. `overflow` anything but `visible` cuts a child off at the box's
edge, and an absolutely positioned menu is a child like any other.

Three tests, and jsdom does no layout, so the geometry is supplied — which is
right here, because what is being pinned is the decision and the decision was
reading the wrong number. A dialog ending at 540 with the button at 480 flips
the menu up although the window has 460 px below it; a dialog ending at 900
leaves it pointing down. On the old line the first of those fails.

### 2026-08-20 — A summary comes back in the language that was spoken

> I když transkriptíš angličtinu, resp jiný jazyk

The progress bar read **Kontroluji češtinu ve shrnutí** over an English
transcript. The message was true, which is what made it worth reporting: a
recording in anything but Czech was summarised, then **translated into Czech**,
then reviewed as Czech.

So an English interview could not be summarised in English at all.

#### Why it was wrong, and it is not the message

Two reasons, and the second is the one that decides.

The summary was doing another tab's job. **`Překlad` is a tab of its own**, and
wanting a summary in a different language is exactly what it is for. The summary
translating on its own initiative left no way to have the other thing — the one
the reader might reasonably expect from a tab called *Shrnutí*.

And it was a decision nobody had made. It reads like a translation of an
English text because that is precisely what it is, twice over: a summary written
in English, machine-translated, then corrected by a prompt that exists to
remove translationese.

Asked, and the owner chose: **the summary follows the recording.**

#### What was actually forcing it

The prompts were already right. `summary_notes_prompt` says *Piš ve stejném
jazyce jako přepis*, and all three of `summary_prompt`'s variants say *Piš ve
stejném jazyce jako podklady a nic nepřekládej*.

Two things overrode them:

- **`CZECH_NOTE`, appended to every summary instruction.** It tells the model to
  write flowing Czech, mind the cases and avoid English turns of phrase — which
  over an English summary is an instruction to translate, and was obeyed as one.
  It is added only for Czech now.
- **The translate-and-review steps.** Gone, along with
  `czech_summary_translation_prompt` and the three progress captions that
  existed only to narrate them.

#### The cached summaries

`output_source_hash` already keys summaries by source language, so the key
changes **only where the behaviour did**: a Czech recording's stored summary is
still exactly its summary and nothing of it regenerates. A recording in any
other language gets a new key, because handing back a Czech summary from the old
pipeline as though it were what this one produces would be the same class of
lie this whole day has been about — a stored thing speaking for a present it no
longer describes.
