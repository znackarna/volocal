# 2026-08-20

### 2026-08-20 — Online import stopped after a megabyte, and the megabyte is the diagnosis

The owner pasted a YouTube link into *Online služba* and got back, inside the
Czech dialog, a line of yt-dlp's English:

```
ERROR: unable to download video data: HTTP Error 403: Forbidden
```

Two separate things were true at once, and separating them is most of the work.

#### The link in the screenshot no longer exists

`qkEl5hPXCXM` returns 404 from YouTube's own oembed endpoint, and every player
client answers *Video unavailable*. So the exact reproduction from the picture
cannot be run again — the video was taken down between the attempt and the
diagnosis.

That is not the fault, though, and believing it was would have closed the
report. The message in the picture is a **403 on the media data**, which can
only be reached *after* extraction succeeded — when the owner tried it, the
video was there and yt-dlp had already read its formats. Something else refused
the audio.

#### Every video failed, at the same place

`dQw4w9WgXcQ` — public, four minutes, certainly present — with the arguments
`online_import.rs` actually passes:

```
[info] dQw4w9WgXcQ: Downloading 1 format(s): 251
ERROR: unable to download video data: HTTP Error 403: Forbidden
```

So the feature was broken for everything, not for one link.

What located it was asking *how much* arrives before the refusal rather than
*whether* anything does. With `--http-chunk-size 10K` the bar climbs to 28.4 %
and stops; with `100K`, to 26.2 %. Both leave about **950 KB** on disk out of
3.27 MB. A ten-kilobyte ranged request — yt-dlp's `--test` — succeeds outright.

An address that serves a megabyte and then refuses is not an expired address, a
blocked address or a rate limit. It is YouTube's **PO token** condition: the
media URL its current default players hand out is good for a preview and needs
a token this application has no way to mint before it will serve the rest. The
first megabyte is the tell, and it is why the failure reads as a network error
when it is an authorisation one.

#### The embedded player's address carries no such condition

Downloading the same format through each client, in full rather than as a
sample, gives one answer:

| client | result |
|---|---|
| `web_embedded` | **3.27 MB, complete** |
| `android_vr` (a default) | 403 after ~1 MB |
| `web`, `mweb`, `android`, `tv_simply` | no audio-only format offered at all |
| `tv` | *The page needs to be reloaded* |
| `ios` | no audio-only format offered |

So `online_import.rs` now passes:

```
--extractor-args youtube:player_client=web_embedded,default
```

Order is the whole of it. `default,web_embedded` still fails — yt-dlp keeps the
first client's address for a duplicate format id, and with the defaults first
the 403-prone address wins the tie. Named first, the embedded player's address
is the one that gets downloaded; `default` stays behind it as the fallback for
what that player will not open.

The argument is addressed to `youtube:` and reaches no other extractor, which
matters here more than usual: what this application supports is what yt-dlp
supports, 1752 sites as counted on 16 August, and a YouTube repair must not be
a change to any of the other 1751.

#### Verified

Full audio through the application's own pipeline — `bestaudio/best`,
`--extract-audio --audio-format m4a --audio-quality 0` — on three videos:
`jNQXAC9IVRw` (0:19, 515 KB), `9bZkp7q19f0` (4:13, 12.2 MB), `kJQP7kiw5Fk`
(4:42, 14.2 MB). All three complete; before the change all three stopped at a
megabyte. `cargo fmt`, `cargo clippy --all-targets -D warnings` and the 215
tests are clean.

#### What was not done, and why

**yt-dlp was not updated.** The natural first guess for a YouTube breakage is a
stale binary, and `components.json` pins `2026.07.04` — which is, today, the
newest stable release there is. Nothing to move to.

**No PO token provider was added.** Minting one means a second runtime service
beside yt-dlp and deno, for a feature that now works without it. If the
embedded player is closed off later, that is the decision to reopen, and this
entry is the argument for it — not a reason to build it in advance.

**The dialog still shows yt-dlp's English inside Czech copy.** That is how the
owner could report this at all: the tail of stderr is what identified a 403
rather than a dead link. A translated summary would have said *stahování se
nezdařilo* and told nobody anything. Worth revisiting as its own piece of work,
with the raw text kept somewhere reachable.

### 2026-08-20 — The setup fails on somebody else's network, and the application had thrown away the reason

Second report of the day, from a machine that is not here: at home the
components download, at a friend's house the first run ends on *Instalace se
nezdařila* with two red lines, both saying **Nepodařilo se spojit se serverem**
and then a huggingface.co URL over four lines.

That message names the one thing the reader cannot act on. Which server it was
is in the sentence; **why it did not answer is not**, and the difference between
a name that does not resolve, a proxy nobody configured, an antivirus opening
the connection, a firewall, and a cable that is out is the whole of the repair.

The reason was not missing. It was collected and discarded. `download_file`
already put the failure into `UserMessage::detail`, and `detail` is by design
only shown when the dictionary has *no* entry for the code — and
`download.connection_failed` has one. So the better the message got, the less
it said.

#### What is on screen now

```
Nepodařilo se spojit se serverem huggingface.co: client error (Connect):
dns error: No such host is known. (os error 11001)
```

The host instead of the whole address — a repository path, a forty-character
commit and a file name are four lines of small red type that answer nothing —
and then the innermost cause. `connection_cause` drops reqwest's outermost
layer, which reads *error sending request for url (…)* and only repeats what
the sentence already said, and joins what is under it.

`download.rejected` gained the status code for the same reason: *Server odmítl
soubor vydat* is equally true of 403, 404 and 451, and they are three different
problems.

**This is English inside Czech copy, and it is the second time today the raw
technical text is what made a report actionable** — the yt-dlp 403 above was
identified from exactly such a line. `Copy is for people` still holds for
everything a person can act on; a transport failure on a machine nobody here
can touch is not that.

#### The instrument, because the fault is not reproducible here

Everything works on this network, so there is nothing to debug — which is the
case the test-card rule was written for. `scripts/network-check.ps1` runs on the
machine that cannot download and separates the steps the application performs
in one breath:

- what the interfaces and their DNS servers are;
- whether a proxy is configured in Windows, in the environment, or by autoconfig
  — the classic works-in-the-browser-fails-in-the-application difference, since
  a proxy set in Windows is not a proxy set in the environment;
- which antivirus is installed, so that the certificate issuer below is
  recognisable when it turns out not to be Amazon's;
- per host — `huggingface.co`, `us.aws.cdn.hf.co`, `cdn-lfs.hf.co`, and the two
  GitHub hosts the programs come from — the name lookup, then **every address it
  resolves to** separately, then the secure handshake and **who issued the
  certificate**;
- and last the real thing: the first 64 KB of the speech-detection file,
  through the redirect, which is the only step that can fail with everything
  above passing.

Two details worth keeping. It is written in **pure ASCII with CRLF**: Windows
PowerShell 5.1 reads a `.ps1` as ANSI unless it carries a BOM, and one em dash
in a comment made the whole file a parse error on the first run. And an address
family is chosen per address rather than left to the client — a machine with no
IPv6 route otherwise answers eight AAAA records with eight lines of *Rodině
adres soketu neodpovídá žádná z nalezených adres*, which reads as eight faults
in a host that is perfectly fine. Those are reported as skipped now, and the
handshake is made through an address that actually answered.

A report where half the lines say FAIL on a healthy machine cannot be read, and
this one is going to be read by somebody standing in a friend's living room.

#### Not decided yet, deliberately

No mirror, no fallback host, no retry policy. Each of them is a guess at a cause
that has not been measured: a mirror repairs a blocked name and does nothing for
a proxy or an intercepted handshake. The measurement comes first — that is the
whole point of the script — and 1.2.16 ships the two things that are right
regardless of the answer: the working online import, and a failure that says
what it was.

### 2026-08-20 — Correction: the 1.2.16 commit carries the presentation site as well

`ffdab3a`, whose message is entirely about the online import and a download that
says why, also contains the whole of `docs/site/` and the records of 18 and 19
August — about ten thousand lines that have nothing to do with the release it
names.

Nothing was lost and the tree is right. What is wrong is the record, which is
the thing this folder exists to keep.

How it happened is worth writing down, because the shape recurs. The
presentation site had been committed **locally and never pushed**, so `main`
here was one commit ahead of `main` there. A branch taken from the local `main`
therefore carried that commit too, and GitHub computes a pull request's diff
against *its* `main` — so the review, the checks and the squash all took in work
nobody had put up for review. The commit that came back is honest about what it
was written for and silent about half of what it contains.

**The lesson is one command**: `git log --oneline origin/main..main` before
branching. A local commit that has never been pushed is invisible in every view
that matters — `git status` is clean, the diff against `HEAD` is empty, the
branch looks like it was taken from what is on the server. Only that comparison
shows it.

Not rewritten, deliberately. `main` is public and the release is built from it;
a force-push to correct a message would cost more than the message is worth, and
this repository's rule for a superseded record is to write the correction after
it rather than to edit the past quietly. So: **`ffdab3a` is two pieces of work,
and this is the second one's name.**
