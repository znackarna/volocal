### 2026-10-04 — volocal-tui asks the terminal whether it is light

The owner ran `volocal-tui` in a light terminal and saw black bands: the
header, the footer, the selected row and the dialogs were painted in the
window's dark surfaces. The gallery, drawn in both palettes, looked right. The
program had chosen dark always, because a terminal does not say what its
background is unless asked, and the light palette came only with
`VOLOCAL_THEME=light`, which nobody sets.

It now asks at start. `terminal-colorsaurus` (MIT or Apache-2.0, what `bat` and
`delta` use) sends the standard question for the background colour together
with one every terminal answers, so a terminal that cannot tell is known within
a moment instead of after a wait; the answer chooses the window's light or
dark palette. Windows Terminal answers from version 1.22, and so do most
terminals at the other end of SSH. Without an answer `COLORFGBG` is read where
a terminal sets it, and then dark, as before. `VOLOCAL_THEME=light` or `dark`
still decides when set. The question is asked only with the window's own
colours (full or 256): with sixteen the colours are the terminal's own, and the
old Windows console is never asked at all.

Verified: clippy with `-D warnings` and the 24 tests of `volocal-tui`, among
them `COLORFGBG` read light only for a white background, pass for the Windows
target under Wine. A run in a pseudo-terminal under Wine started, drew in the
dark palette and quit cleanly, but Wine's console does not pass the question
through, so the answer itself has not been seen: that needs Windows Terminal.

Files: `src-tauri/src/bin/volocal-tui/theme.rs`, `src-tauri/Cargo.toml`,
`src-tauri/Cargo.lock`, `docs/tui-plan.md`.

### 2026-10-04 — The tests run again on Windows: the manifest goes into them too

`Checks` was red on `c25ba77` (Volocal 1.3.0), and so was `cargo test` on the
owner's machine: the library's test program stopped before running a test,
with `STATUS_ENTRYPOINT_NOT_FOUND`. Bisected: `b18f29a` passes, `1a0c48e` (the
window sees a run of the command line) fails. Comparing the two test
programs' import tables showed why. The failing one imports the whole window
stack — `comctl32.dll!TaskDialogIndirect`, `SetWindowSubclass`, user32, gdi32,
dwmapi, ole32 — because a new test of the transcription queue reaches
`Report::Window`, and with it Tauri's runtime. `TaskDialogIndirect` exists only
in Common Controls 6, which Windows gives a program only when its manifest asks
for it. Tauri puts that manifest into the application's programs, not into
test programs.

The fix is the one Tauri's documentation gives for tests: `build.rs` switches
Tauri's own manifest off (`WindowsAttributes::new_without_app_manifest`) and
hands the same file — `src-tauri/windows-app-manifest.xml`, copied unchanged
from tauri-build 2.6.3 — to the linker for everything it links
(`/MANIFEST:EMBED`, `/MANIFESTINPUT`), on Windows with MSVC only. The window,
`volocal-cli` and `volocal-tui` carry exactly the manifest they carried before;
the test programs now carry it as well. No application code changed.

Verified: `cargo test` 325 + 24 + 24, clippy and fmt clean; the Common Controls
line is in `volocal.exe`, `volocal-cli.exe` and `volocal-tui.exe`;
`npm run build` and `npm test` (339).

Files: `src-tauri/build.rs`, `src-tauri/windows-app-manifest.xml`.

### 2026-10-04 — volocal-tui plays a transcript's sound, where it runs locally

Asked for by the owner, with the keys, the behaviour and the method set out.
The plan of 3 October offered no playback because over SSH the sound would
come out of the remote computer; that still holds, and playback is offered
only where none of `SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY` is set.

**What it does.** In the reader the space bar plays from the block under the
cursor, pauses, and resumes; if the cursor was moved to another block while
paused, it starts there instead. `,` and `.` go 5 s back and on, kept inside
the recording: both are typed without AltGr on a Czech keyboard, and neither
was taken (`←`/`h` is back to the archive). The block that sounds has `▶` on
its first line and the bar on the rest; when the sound reaches another block
the cursor goes with it, so the block stays on screen, and a cursor moved by
hand stays until then without stopping anything. The header shows `▶ 12:04 /
52:18`, or `‖` while paused. Leaving the transcript by any key stops the
sound. The footer and the help show the keys only while playback is offered.

**How.** The first play of a recording has ffmpeg — the one in Volocal's tools
folder — write a 16-bit mono WAV at 48 kHz, on a thread of its own, while the
foot of the screen says *Připravuji zvuk…*; a play asked for meanwhile waits,
and the latest one wins. Every start is then a seek to the exact sample of the
time, read straight from the WAV's `data` chunk: no MP3 table is involved, so
the 8-second error of the Janka reproduction cannot happen here. Stored word
times are not touched. ffmpeg gets `-nostdin` and a closed input, because in a
raw terminal it would otherwise read the program's keys.

The copy lives in the window's `playback-cache` as `<id>-<fingerprint>.wav`,
the fingerprint of the source's path, size and modification time computed as
the window computes its own. A replaced or moved source is therefore copied
again rather than played stale, and the window's tidying of `<id>-*` when a
recording is deleted or moved takes these copies with its own. The other way
round, the window replacing its `.m4a` for an MP3 also removes this program's
copy of the same recording, which costs one conversion and nothing else. The
copies of the three most recently played recordings are kept; an hour is
about 345 MB.

Played through rodio 0.22 (MIT or Apache-2.0) with no decoder, only its output
to the sound card, and only `volocal-tui` uses it. Its two messages that would
print over the screen — a stream error and its farewell on drop — are
silenced. Each start makes a new player and drops the old one, which stops it
at once; emptying a player would wait for the audio thread. No sound device,
no ffmpeg, a missing source or a failed copy is said in one line, and
playback is then no longer offered for that transcript; everything else works
as before.

Verified: clippy with `-D warnings` for the Windows target; under Wine the 34
tests of `volocal-tui` (among them: the space bar, pause and resume in and out
of the block, skips clamped at both ends, the cursor following the sound into
the next block, a moved cursor not stopping it, the keys absent over SSH, no
sound device said once, a failed copy and a copy for another recording, the
WAV header with ffmpeg's `LIST` chunk, the fingerprint, the tidying), the 24 of
`volocal-cli`, and the engine's 322 with the three that fail under Wine only.
A WAV written by the system's ffmpeg with the same arguments has the layout
the reader expects, and a 7.0 s MP3 came out as exactly 7.0 s. Not heard: no
sound card here, and the program has not played on Windows yet.

Files: `src-tauri/src/bin/volocal-tui/{playback,app,reader,words,theme,main}.rs`,
`src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `docs/tui-plan.md`.
