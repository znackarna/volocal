### 2026-10-03 — Menus are popovers (audit item 14)

The recording's menu (`ActionMenu`), the save menu in the improved-transcript
dialog (`DocumentSaveMenu`) and the transcript's context menu each carried the
same two document listeners: a press outside closes, Escape closes. They are
native popovers now, through `src/Popover.tsx`: `useMenu()` for a menu behind a
button, `PointedPopover` for the context menu, which has no button. The other
two copies the audit counted go with their own items — the archive calendar
with item 7, `Select.tsx` with item 9.

**A menu behind a button is named by it (`popovertarget`)**, not opened by the
owner's state calling `showPopover`. The first version did the latter and a
test page showed what it cost: the browser closes an open popover on the press,
before the click, so a second click on the same button closed the menu and the
click opened it again. With `popovertarget` the browser knows the button is the
menu's own and closes it; it also gives the button Enter, Space and
`aria-expanded`. The menu stays in the page, hidden, and renders its items in
`beforetoggle` (with `flushSync`), so it never shows empty.

What changes for the reader:

- **No dialog can cut a menu off.** A popover sits in the top layer. The save
  menu used to measure the nearest scrolling box to decide whether to open
  upwards (the fault of 20 August, when `.dialog` cut it in half); that
  measurement is gone.
- **Placement is CSS.** Anchored to its button (`position-area: bottom
  span-left`, 6 px gap), turned upwards at the window's edge
  (`position-try-fallbacks: flip-block`). Before, the recording's menu always
  opened downwards.
- **Escape inside a dialog closes the menu, not the dialog.** It used to close
  both: the menu's listener on the document and the dialog's on its element
  both answered the key. `useDialog` now leaves Escape to an open popover.
- A closed popover is hidden by `:not(:popover-open) { display: none }`: the
  menus' own `display: flex` is the author's and would beat the browser's
  `display: none`. A test page showed the closed menu staying on screen.

Verified: `npm run build`, `npm test` (334; the context menu's three tests of
its own listeners became two of the popover contract, the save menu's geometry
tests became popover tests). In a Chromium 152 test page with the same CSS:
6 px under the button with right edges aligned, past the edge of a scrolling
box without being cut, flipped upwards at the window's bottom, a second click
on the button closes and stays closed, Escape and a click outside close.
**Not yet seen in the running app**: the dev build closed itself twice and
opened no debugging port, so the WebView itself (154) was not driven.

To confirm in the app (`npm start`):

1. Archive: open a recording's ⋯ menu. It sits under the button, right edges
   aligned. Click ⋯ again: it closes. Open it, press Escape: it closes. Open
   it, click elsewhere: it closes. Walk into *Jazyky* and back.
2. On the last row of a long archive scrolled to the bottom, the menu opens
   upwards instead of off the window.
3. Transcript: right-click a block. The menu opens at the pointer; Escape,
   a click elsewhere, scrolling and resizing the window each close it.
4. Improved transcript dialog: *Uložit* opens TXT and MD whole. With the menu
   open, Escape closes only the menu; a second Escape closes the dialog.
5. Both themes: the menus keep their panel colour and shadow.
