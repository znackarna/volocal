# 2026-09-01

### 2026-09-01 — The release script asks whether the version is already out

1.2.22 was published at 23:01 on 31 August and this session went on building the
same version for another three-quarters of an hour. Nothing asked, and the
promise to check `gh release list` after handing over a publish command — made
on 26 August after exactly this — had been broken twice by then.

So the script asks, and asks `origin` rather than this clone: a tag can be
pushed from anywhere, and the question is whether the world already has this
number, not whether this machine has fetched it. It asks before the twenty
minutes rather than after, beside the clean-tree guard and for the same reason —
the dangerous shape is an installer bearing a version somebody's copy already
has, carrying different bytes.

Being unable to ask is a warning, not a stop. No network is not evidence of
anything.

Checked against the real tags rather than reasoned about: `v1.2.22` stops it,
`v1.2.23` and a made-up `v9.9.9` pass.

**And the thing it could not have caught.** The guard was written while 1.2.23
was building, which left it uncommitted when the installer finished — so the
tree no longer matched what had been built, and the second pass would have
refused. It was set aside as a patch, the release went out from a clean tree at
`1c35d21`, and it is committed now. `scripts/release.ps1` is not compiled into
the installer, so nothing about that release is less traceable for it; the point
is that a repair to the release machinery cannot land in the middle of a
release. The next one goes in before the build or after the publish.

`Cargo.lock` rides along, since the build rewrites it with every version bump
and it has now been a separate stray commit three releases running.

Verified: 1.2.23 published 22:01:32 UTC, the installer on the release is
9 605 700 bytes — the file measured on this disk — `latest.json` and the
signature beside it, and `site.yml` redeployed the page a second later.

Files: `scripts/release.ps1`, `src-tauri/Cargo.lock`.

## Splitting the large React components: stage one, the tests that come first

`refactor_codex.md` sets out ten stages for taking `Detail.tsx`,
`Settings.tsx` and `App.tsx` apart by responsibility. The work runs on a
`refactor` branch — an exception to the two-branch rule, asked for so that ten
stages do not sit on `dev` half-finished.

**Checked before starting, because the brief said to.** Every figure in it is
right: 3 507 lines and 53 pieces of state in `Detail.tsx`, 2 929 and 22 in
`Settings.tsx`, 1 960 and 33 in `App.tsx`, 187 frontend tests, 248 Rust tests,
build and clippy clean.

**Stage one is characterization tests, and it is the biggest part of the
brief.** `App.tsx` had no test that rendered it at all; `Detail` had five and
`Settings` three. What is written here is the Detail half of it, twenty-nine
tests across four files, none of which names a hook or a component — every one
opens the whole screen and asks it what a reader would ask. That is the point:
the extraction that follows must not have to rewrite the tests that judge it.

The setup moved out first. `src/detail/fixtures.ts` holds the data and the API
double, `src/detail/harness.tsx` mounts the screen. They are two files because
a `vi.mock` factory is hoisted above the imports of the file it is written in:
a factory can reach `fixtures.ts`, which imports nothing of the application,
but reaching `harness.tsx` would pull in `Detail` and, through it, the very
module being mocked. The API double is built once and exported rather than made
fresh per call, because a test of a feature that writes has to reach the spies
the screen is calling.

**What each file pins, and why that one.**

*Search* (`search.test.tsx`, eleven). The one that matters is that closing the
bar forgets the search. Whether the bar is up and what is written in it are two
pieces of state that reset together today; split between two owners they would
stop doing so and nothing would fail to compile. Also the two-character floor,
the count wrapping past the last hit and before the first, Enter and
Shift+Enter, a new query returning to the first hit, and `found` sitting on
exactly one block.

*Notes* (`notesSection.test.tsx`, nine). The one to keep is that deleting asks
first. A note is the only text in the application a person wrote themselves and
that cannot be produced again; the question in front of the deletion is a
decision, not an accident of where the state currently sits.

*Corrections and the shell boundary* (`editing.test.tsx`, nine). Seven for
correcting a block. Two for the boundary the brief names: transcription and
speaker separation are asked for through the shell, which puts a question
first, and a declined transcription must leave no progress bubble behind —
that state used to survive the refusal with no way out of it.

**Three tests were wrong before the code was.** A key press was sent to
`window`, which is not an element and has no `closest`; a class name was
guessed; an assertion dropped a full stop. All three were the test's fault, and
none of them found anything wrong with the screen. Worth recording because it
is the expected shape of this stage: characterization tests written against a
working product mostly fail on the way the question was asked.

Verified: 216 frontend tests pass, TypeScript clean, and the five tests that
existed before are unchanged and still pass.

Files: `src/detail/fixtures.ts`, `src/detail/harness.tsx`,
`src/detail/screen.test.tsx`, `src/detail/search.test.tsx`,
`src/detail/notesSection.test.tsx`, `src/detail/editing.test.tsx`.

## Stage one finished: Settings and the shell

The other half of the characterization tests. 187 tests at the start of the
day, 256 now.

**`SettingsScreen`, eleven tests.** The tabs are the seam the split will follow,
so what is pinned is what has to survive it. That pressing a tab is a choice
and is remembered, while being sent to one is not — arriving from a notice must
not overwrite where the reader last was. That a remembered tab name this build
no longer has opens the first tab rather than an empty panel, which is what
made renaming `application` safe. And the rule the split is most likely to
break: a switch writes the whole settings object, so a tab component saving only
its own field would drop what the other six hold. The dictionary gets four,
being the one tab with data and CRUD of its own.

**`App.tsx`, fourteen tests, and nothing rendered it before.** The two screens
it owns had tests; the thing that decides which is open and what may start had
none. It is the hardest of the three to mount because almost nothing it does
starts on screen — seven backend event streams, the webview's own drag-and-drop
channel, the updater — and the fixtures hand all of them to a test.

The one that matters is the question before a run. With speaker separation off,
transcription is a direct call; with it on, the question comes first and nothing
starts until it is answered. Declining must start nothing at all.

**Two things this stage found out, neither of them a fault.**

The shell polls the watched folder unconditionally. There is no check on
`watch_folder_enabled` in the frontend at all — the backend answers with nothing
when the folder is off, which is what makes `scan_watch_folder` safe to call
every five seconds. Worth writing down because it is exactly the kind of thing
a move can quietly *improve*: a `useWatchFolder` that reads the setting and
skips the call would change when a folder switched on in Settings is noticed.

And `api.detail` in the shell's fixtures answered about a fixed recording rather
than the one the archive had been given, so opening an untranscribed recording
still showed a transcript and the empty state carrying `Přepsat` could not be
reached. A fixture that does not follow the test's own setup is a test that
cannot fail for the right reason.

**Naming.** `screen.fixtures.ts` and `screen.harness.tsx` in each of
`src/detail/`, `src/settings/` and `src/app/`. `scripts/i18n.mjs` skips both
suffixes now, on the argument it already made for `.test.`: their strings are
read by whoever runs the tests and by nobody else, and a Czech transcript in a
fixture is the point of the fixture.

Verified: 256 frontend tests, 248 Rust tests, `npm run build` clean, clippy
clean. No file outside `src/detail/`, `src/settings/`, `src/app/` and
`scripts/i18n.mjs` was touched — the product has not changed yet, which is the
whole point of a stage that only writes tests.

Files: `src/settings/screen.fixtures.ts`, `src/settings/screen.harness.tsx`,
`src/settings/screen.test.tsx`, `src/app/screen.fixtures.ts`,
`src/app/screen.harness.tsx`, `src/app/screen.test.tsx`.
